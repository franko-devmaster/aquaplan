## 09-13 — Bugfix écran délégations + traduction round-add-order

- **Epic parent** : Epic E Bugfix & dette technique
- **Estimation** : M
- **Dépendances** : aucune (démarrage immédiat Sprint 1)

### User story
**En tant qu'** administrateur,
**Je veux** que l'écran `/admin/delegations` soit à nouveau fonctionnel et affiche les délégations du tenant, et que la clé i18n `orders.analysisPrograms` soit correctement traduite dans le dialog d'ajout de mandat à une tournée,
**Afin de** pouvoir gérer les délégations de rôles et de ne plus voir de clés brutes dans l'UI.

### Contexte métier
Deux défauts ont été identifiés en QA v0.8 : (1) l'écran des délégations est inutilisable — aucune délégation ne s'affiche, l'utilisateur est bloqué ; (2) le dialog `round-add-order-dialog` affiche la chaîne brute `orders.analysisPrograms` au lieu du libellé traduit. Ces deux défauts doivent être corrigés en priorité avant tout développement v0.9 pour ne pas empoisonner les tests.

### Critères d'acceptation

**Scénario 1 — Happy path : écran délégations opérationnel**
```gherkin
Étant donné un tenant avec au moins 2 délégations créées en base
Et un utilisateur Admin connecté
Quand il navigue vers /admin/delegations
Alors la liste des 2 délégations s'affiche sans erreur console
Et chaque ligne présente : utilisateur délégué, rôle, période, statut
Et l'utilisateur peut créer, éditer et supprimer une délégation
```

**Scénario 2 — Edge case : tenant sans délégation**
```gherkin
Étant donné un tenant sans aucune délégation
Quand l'Admin ouvre /admin/delegations
Alors un empty-state s'affiche (ex. "Aucune délégation configurée")
Et aucune erreur n'apparaît en console ni dans les logs backend
Et le bouton "Créer une délégation" reste fonctionnel
```

**Scénario 3 — Permission / i18n : clé analysisPrograms traduite**
```gherkin
Étant donné un utilisateur autorisé ouvre le dialog round-add-order-dialog
Quand il consulte le champ de sélection des programmes d'analyse
Alors le libellé affiché est "Programmes d'analyse" en fr, "Analyseprogramme" en de, "Analysis programs" en en
Et aucune chaîne brute "orders.analysisPrograms" n'apparaît dans l'UI
Et un utilisateur non autorisé voit toujours un 403 sur /admin/delegations
```

### Tâches techniques

**Investigation (obligatoire avant code)**
- Inspecter la console navigateur sur `/admin/delegations` (erreur JS ? 401/403 ? 500 ?)
- Vérifier `DelegationsController` : routes, `[Authorize(Roles = ...)]`, filtrage tenant
- Vérifier `DelegationService` : requête EF Core, `Include`, tenant filter global
- Contrôler que le composant Angular est bien standalone et importe ses dépendances
- Vérifier la signature DTO entre backend et NSwag-generated client

**Backend (si root cause backend)**
- Corriger le controller / service / filtrage selon root cause identifié
- Ajouter ou restaurer tests xUnit `DelegationServiceTest` / `DelegationsControllerTest`

**Frontend**
- Corriger le composant `admin/delegations/*` (imports, injection, signals)
- Ajouter la clé i18n `orders.analysisPrograms` dans `assets/i18n/{fr,de,en}.json`
- Vérifier l'usage du pipe `translate` dans `round-add-order-dialog.component.ts` / template

**Tests**
- Non-régression manuelle : création/édition/suppression délégation
- Non-régression manuelle : ouverture round-add-order-dialog multi-langues
- Si bug backend : tests xUnit couvrant le happy path + filtrage tenant

## 09-06 — Colonne Actions LDP : menu 3 points verticaux

- **Epic parent** : Epic B LDP workflow unifié
- **Estimation** : M
- **Dépendances** : aucune (peut démarrer en parallèle du bugfix 09-13)

### User story
**En tant qu'** administrateur ou requérant,
**Je veux** une colonne "Actions" à droite de la colonne "Statut" dans la liste des LDP (section Réseau) avec un menu 3 points verticaux (Éditer, Valider, Supprimer) conditionné par les permissions et l'état du LDP,
**Afin de** disposer d'un point d'entrée unique pour toutes les actions LDP et de supprimer l'écran Admin dédié.

### Contexte métier
Aujourd'hui les actions LDP sont éclatées : validation dans `/admin/validation-queue`, suppression via corbeille sur `/sampling-locations`, édition via clic sur la ligne. Ce morcellement multiplie les écrans et les clics. Centraliser les 3 actions derrière un menu kebab aligne l'UX sur les patterns Material Design et prépare la suppression complète de `/admin/validation-queue`.

### Critères d'acceptation

**Scénario 1 — Happy path : menu kebab avec 3 actions**
```gherkin
Étant donné un Admin sur /sampling-locations section Réseau
Et un LDP non validé, non rattaché à un mandat
Quand il clique sur le menu 3 points verticaux de la ligne
Alors un mat-menu s'ouvre avec 3 items visibles : "Éditer", "Valider", "Supprimer"
Et la colonne "Actions" est positionnée à droite de la colonne "Statut"
Et le bouton corbeille d'avant n'existe plus
```

**Scénario 2 — Edge case : LDP validé et rattaché**
```gherkin
Étant donné un LDP déjà validé (IsValidated=true) et rattaché à au moins un mandat
Quand un Admin ouvre le menu kebab de cette ligne
Alors seul l'item "Éditer" est présent
Et "Valider" est masqué (LDP déjà validé)
Et "Supprimer" est masqué (LDP rattaché à un mandat)
```

**Scénario 3 — Permission : rôles non-Admin**
```gherkin
Étant donné un utilisateur Requérant (non-Admin)
Quand il ouvre le menu kebab d'un LDP non validé
Alors il voit "Éditer" et "Supprimer" (si non rattaché) mais pas "Valider"
Et un appel direct POST /api/sampling-locations/{id}/validate retourne 403 Forbidden
```

### Tâches techniques

**Frontend**
- `pages/sampling-locations/sampling-location-list.component.ts` :
  - Ajouter colonne `actions` dans `displayedColumns` positionnée après `status`
  - Template : `<button mat-icon-button [matMenuTriggerFor]="menu"><mat-icon>more_vert</mat-icon></button>`
  - `<mat-menu #menu>` avec 3 items conditionnés (`*ngIf` ou `@if`)
  - Supprimer l'ancien bouton corbeille
- `assets/i18n/{fr,de,en}.json` : clés `samplingLocations.actions.{edit,validate,delete}`

**Backend**
- Vérifier que l'endpoint `POST /api/sampling-locations/{id}/validate` existe et est `[Authorize(Roles = "Admin")]`
- S'assurer que le DTO liste expose `IsValidated` et `CanDelete` (voir story 09-07)

**Tests**
- `tests/AquaPlan.Api.Tests/Controllers/SamplingLocationsControllerTest.cs` : vérifier attributs auth + route validate
- Non-régression UI manuelle : 3 états de ligne (non validé non rattaché / validé non rattaché / validé rattaché)

## 09-07 — Dialog édition LDP : 4 boutons + canDelete API

- **Epic parent** : Epic B LDP workflow unifié
- **Estimation** : M
- **Dépendances** : **09-06** (colonne Actions en place pour y connecter le dialog)

### User story
**En tant qu'** administrateur,
**Je veux** que le dialog d'édition LDP propose 4 boutons en bas (Annuler, Supprimer, Valider, Enregistrer) avec visibilité conditionnée par les permissions et l'état du LDP, et que le backend expose `canDelete`,
**Afin de** pouvoir agir sur un LDP sans quitter l'édition.

### Contexte métier
Le dialog actuel n'offre que Annuler et Enregistrer. L'Admin doit revenir en arrière pour valider ou supprimer, fragmentant le workflow. Le champ `canDelete` (rattachement mandat) doit remonter du backend car le frontend ne peut pas calculer cette information de manière fiable (nécessite une requête sur `orders`).

### Critères d'acceptation

**Scénario 1 — Happy path : 4 boutons Admin sur LDP non validé non rattaché**
```gherkin
Étant donné un Admin ouvre le dialog d'édition d'un LDP non validé et non rattaché
Quand le dialog s'affiche
Alors 4 boutons sont visibles en bas : "Annuler", "Supprimer", "Valider", "Enregistrer"
Et le clic sur "Valider" appelle POST /api/sampling-locations/{id}/validate et ferme le dialog
Et le clic sur "Supprimer" appelle DELETE /api/sampling-locations/{id} après confirmation
```

**Scénario 2 — Edge case : LDP validé et rattaché**
```gherkin
Étant donné un LDP déjà validé et rattaché à un mandat
Quand un Admin ouvre le dialog d'édition
Alors seuls "Annuler" et "Enregistrer" sont visibles
Et "Valider" est masqué (IsValidated = true)
Et "Supprimer" est masqué (canDelete = false)
```

**Scénario 3 — Permission : non-Admin**
```gherkin
Étant donné un utilisateur Requérant (non-Admin)
Quand il ouvre le dialog d'édition d'un LDP
Alors "Valider" est toujours masqué (action Admin-only)
Et "Supprimer" reste visible si canDelete = true (Requérant peut supprimer son propre LDP selon convention)
Et l'endpoint DELETE applique la politique d'autorisation backend
```

### Tâches techniques

**Backend**
- `ISamplingLocationService.GetByIdAsync` : inclure calcul `CanDelete` (vérifier absence rattachement mandat ou via `orders.sampling_location_id`)
- `SamplingLocationDto` : ajouter propriété `bool CanDelete`
- Alternative : nouvel endpoint léger `HEAD /api/sampling-locations/{id}/can-delete` → 200/409
- Vérifier attributs `[Authorize(Roles = "Admin")]` sur validate, `[Audited]` sur delete

**Frontend**
- `pages/sampling-locations/sampling-location-form-dialog.component.ts` (ou nom équivalent) :
  - Template mat-dialog-actions : 4 `<button mat-button>` conditionnés
  - Récupérer `canDelete` depuis le DTO GET /api/sampling-locations/{id}
  - `isAdmin()` via service Auth
  - Confirmation native Angular Material dialog sur Supprimer
- i18n : clés `samplingLocations.form.actions.{cancel,delete,validate,save}`

**Tests**
- `SamplingLocationServiceTest` : `GetById_WhenLocationLinkedToOrder_ShouldReturnCanDeleteFalse` / `...NotLinked_ShouldReturnTrue`
- `SamplingLocationsControllerTest` : vérifier DTO renvoyé contient CanDelete
- Non-régression UI : 4 combinaisons état × rôle

## 09-01 — Entité SamplingContainer + migration + backfill legacy barcode

- **Epic parent** : Epic A Prélèvement multi-flacons + scan caméra + résumé tournée
- **Estimation** : L
- **Dépendances** : v0.8 (Container, profils rattachés à un contenant, mandats ↔ programmes)

### User story
**En tant que** préleveur,
**Je veux** pouvoir enregistrer **un code-barres par contenant physique** d'un prélèvement (et non plus un unique code pour tout le mandat), avec backfill automatique des codes legacy existants,
**Afin de** tracer chaque flacon individuellement et préparer le scan multi-flacons.

### Contexte métier
Aujourd'hui un prélèvement stocke un seul `sample_barcode` dans la table `samplings`. Un mandat peut pourtant nécessiter plusieurs flacons (ex. bactério + chimie + pesticides = 3 contenants). Le modèle actuel oblige à saisir un seul code pour l'ensemble, créant des collisions et empêchant la traçabilité par flacon. La nouvelle entité `SamplingContainer` associe chaque prélèvement à plusieurs contenants, chacun avec son propre barcode. Le champ legacy est conservé en lecture pour rétro-compatibilité mais n'est plus écrit par l'UI v0.9.

### Critères d'acceptation

**Scénario 1 — Happy path : migration et backfill**
```gherkin
Étant donné une base AquaPlan v0.8 avec des samplings contenant sample_barcode renseigné
Quand la migration "AddSamplingContainers" est appliquée
Alors la table "sampling_containers" existe avec colonnes Id, SamplingId, ContainerId, Barcode, BarcodeScannedAt, TenantId, CreatedAt
Et pour chaque sampling avec un sample_barcode non nul, une ligne sampling_containers est créée en best-effort
  - ContainerId = Id du contenant du 1er profil du 1er programme du mandat
  - Barcode = ancienne valeur sample_barcode
  - BarcodeScannedAt = null
Et un index unique filtré (TenantId, Barcode) WHERE Barcode IS NOT NULL est créé
Et la colonne samplings.sample_barcode est conservée (legacy, read-only UI)
```

**Scénario 2 — Edge case : mandat sans programme ni profil**
```gherkin
Étant donné un sampling dont le mandat n'a aucun programme rattaché (cas résiduel avant v0.8)
Quand la migration de backfill s'exécute
Alors aucune ligne sampling_containers n'est créée pour ce sampling
Et un enregistrement audit_log de type "SamplingContainerBackfillSkipped" est inséré avec la cause
Et la migration continue sans échouer
```

**Scénario 3 — Permission / intégrité : suppression sampling cascade**
```gherkin
Étant donné un sampling avec 3 sampling_containers associés
Quand le sampling est supprimé (DELETE /api/samplings/{id} autorisé)
Alors les 3 sampling_containers sont supprimés en cascade (FK ON DELETE CASCADE)
Et la suppression d'un Container référencé par un sampling_container est bloquée (FK ON DELETE RESTRICT)
Et l'isolation tenant est respectée (TenantId dénormalisé sur sampling_containers pour query filter direct)
```

### Tâches techniques

**Backend — Domain**
- Créer `src/AquaPlan.Domain/Entities/SamplingContainer.cs`
  - Propriétés : Id, SamplingId, ContainerId, Barcode (nullable), BarcodeScannedAt (nullable), TenantId, CreatedAt
  - Navigations : Sampling, Container
- `Sampling.cs` : ajouter navigation `ICollection<SamplingContainer> SamplingContainers`
- `SampleBarcode` conservé mais marqué `[Obsolete("Legacy v0.8; use SamplingContainers")]` si pertinent

**Backend — Infrastructure**
- `Data/Configurations/SamplingContainerConfiguration.cs`
  - FK SamplingId → CASCADE
  - FK ContainerId → RESTRICT
  - Index unique filtré `(TenantId, Barcode) WHERE Barcode IS NOT NULL`
  - Query filter tenant
- `AquaPlanDbContext` : DbSet
- Migration `AddSamplingContainers` avec backfill SQL :
  ```
  INSERT INTO sampling_containers (id, sampling_id, container_id, barcode, tenant_id, created_at)
  SELECT gen_random_uuid(), s.id,
         (SELECT ap.container_id
            FROM analysis_program_profiles app
            JOIN analysis_profiles ap ON ap.id = app.analysis_profile_id
            JOIN order_analysis_programs oap ON oap.program_id = app.analysis_program_id
           WHERE oap.order_id = s.order_id
           ORDER BY app.sort_order, ap.id
           LIMIT 1),
         s.sample_barcode, s.tenant_id, NOW()
  FROM samplings s
  WHERE s.sample_barcode IS NOT NULL;
  ```
  (à ajuster selon noms exacts de colonnes)

**Backend — Application**
- DTOs : `SamplingContainerDto`, `SamplingContainerInputDto`
- `ISamplingService` : prise en compte de `SamplingContainers` sur GET

**Tests (obligatoires)**
- `tests/AquaPlan.Infrastructure.Tests/Migrations/AddSamplingContainersTest.cs` : migration + backfill sur dataset synthétique (cas avec barcode, cas sans mandat programme, cas multi-profils)
- `tests/AquaPlan.Application.Tests/Services/SamplingServiceTest.cs` : `GetById_ShouldIncludeSamplingContainers`
- Test contrainte unicité : insérer 2 sampling_containers avec même barcode/tenant → échec
- Test isolation tenant

## 09-02 — Endpoint GET /api/orders/{id}/required-containers

- **Epic parent** : Epic A Prélèvement multi-flacons + scan caméra + résumé tournée
- **Estimation** : M
- **Dépendances** : **09-01** (entité en place)

### User story
**En tant que** préleveur,
**Je veux** connaître pour un mandat la liste **unique** des contenants requis (dédupliqués par ContainerId) en agrégeant les profils de tous les programmes du mandat,
**Afin d'** afficher dynamiquement les champs de saisie barcode dans le dialog de prélèvement.

### Contexte métier
Le dialog `sampling-form-dialog` doit générer un champ par contenant à saisir. La liste des contenants dépend des programmes du mandat (v0.8), qui listent chacun des profils, chacun rattaché à un contenant. **Scénario 2 — Edge case : aucun mandat éligible**
