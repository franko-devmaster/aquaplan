## AQ-32 — Mock LIMS — Socle : endpoints REST internes et générateur de résultats

- **Epic parent** : AQ-7 Intégration Limsophy (repurposée "Mock LIMS")
- **Estimation** : L
- **Dépendances** : aucune (démarrage Sprint 1 J+0)

### User story
**En tant qu'** administrateur AquaPlan,
**Je veux** disposer dans le monorepo d'un Mock LIMS accessible via 3 endpoints REST internes + un générateur de résultats réalistes pour 14 paramètres d'eau potable,
**Afin de** prouver la boucle d'intégration LIMS de bout en bout sans dépendre d'un LIMS externe propriétaire.

### Contexte métier
Décision d'architecture v0.92 : abandon de l'intégration Limsophy (AAC Infotray) au profit d'un Mock LIMS interne, standard REST JSON. Objectif : prouver la boucle sans dépendance externe, maîtriser contrats et données de test. Le Mock reste dans `AquaPlan.Api` sous `/api/mock-lims/*` (pas de nouveau process), activé via feature flag `MockLims:Enabled=true` (désactivé en prod par défaut). Les 14 paramètres couvrent pH, conductivité, turbidité, chlore libre/total, nitrates, nitrites, ammonium, Fe, Mn, Cu, E. coli, entérocoques, coliformes totaux, flore aérobie à 22°C. ~5 % des valeurs générées sont hors-normes (réalisme).

### Critères d'acceptation

**Scénario 1 — Happy path : création d'un ordre Mock LIMS**
```gherkin
Étant donné le feature flag MockLims:Enabled=true
Et un Admin authentifié
Quand il appelle POST /api/mock-lims/orders avec un payload valide (orderReference, samplingDate, parameters[])
Alors l'API retourne 201 Created avec { limsOrderId: <guid>, acceptedAt: <iso> }
Et une entrée est persistée dans la table mock_lims_orders
Et un GET /api/mock-lims/orders/{id} retourne le même ordre avec statut "Received"
```

**Scénario 2 — Edge case : génération de résultats avec valeurs hors-normes**
```gherkin
Étant donné un ordre Mock LIMS avec 14 paramètres demandés
Quand un GET /api/mock-lims/orders/{id}/results est appelé
Alors la réponse contient 14 résultats avec {parameterCode, value, unit, referenceMin, referenceMax, isConform}
Et statistiquement ~5 % des résultats présentent value hors [referenceMin, referenceMax] (isConform=false)
Et chaque résultat est déterministe pour un seed donné (reproductibilité tests)
Et le statut de l'ordre passe à "ResultsReady"
```

**Scénario 3 — Permission : feature flag et auth Admin only**
```gherkin
Étant donné le feature flag MockLims:Enabled=false
Quand un Admin appelle POST /api/mock-lims/orders
Alors l'API retourne 404 Not Found (endpoint masqué)
Et quand le flag est true mais un utilisateur non-Admin appelle
Alors l'API retourne 403 Forbidden
Et quand la requête n'est pas authentifiée
Alors l'API retourne 401 Unauthorized
```

### Tâches techniques

**Backend — Domain**
- Entité `MockLimsOrder` : `Id, OrderReference, SamplingDate, Parameters (jsonb), Status, ReceivedAt, ResultsReadyAt`
- Enum `MockLimsOrderStatus { Received, Processing, ResultsReady }`
- Valeur réfs `ParameterReference` (code, unité, min, max) pour les 14 paramètres

**Backend — Infrastructure**
- Migration EF `AddMockLimsOrders` (table + index sur `OrderReference` unique)
- Configuration EF `MockLimsOrderConfiguration`

**Backend — Application**
- Interface `IMockLimsResultGenerator` + impl `MockLimsResultGenerator` (seed configurable pour tests)
- Service `IMockLimsOrderService` + impl : `CreateAsync`, `GetAsync`, `GetResultsAsync`
- DTOs : `MockLimsOrderDto`, `MockLimsCreateDto`, `MockLimsResultDto`

**Backend — API**
- Controller `MockLimsController` sous `/api/mock-lims`
- `[FeatureGate("MockLims")]` sur le controller
- 3 endpoints :
  - `POST /orders` → 201 | 400 | 401 | 403 | 404(flag off)
  - `GET /orders/{id}` → 200 | 401 | 403 | 404
  - `GET /orders/{id}/results` → 200 | 401 | 403 | 404
- `[Authorize(Roles = "Administrator")]` + `[Audited]` sur POST

**Backend — DI**
- Extension `.WithMockLims(configuration)` enregistrée dans `Program.cs` côté API
- Feature flag dans `appsettings.json` : `"MockLims": { "Enabled": false }`

**Tests (obligatoires)**
- `MockLimsOrderServiceTest` :
  - `CreateAsync_WithValidPayload_ShouldPersistAndReturnId`
  - `CreateAsync_WithDuplicateReference_ShouldThrowConflict`
  - `GetResultsAsync_WithFixedSeed_ShouldBeDeterministic`
  - `GetResultsAsync_ShouldProduceApproximately5PercentOutOfRange` (tolérance ±2%)
- `MockLimsResultGeneratorTest` :
  - `Generate_ShouldRespectParameterReferenceRanges`
  - `Generate_WithInvalidParameterCode_ShouldThrow`
- `MockLimsControllerTest` :
  - Attributs HTTP `[HttpPost]`/`[HttpGet]`, routes exactes
  - `[Authorize(Roles = "Administrator")]` + `[FeatureGate("MockLims")]` + `[Audited]`
  - 401, 403 (Requérant/Préleveur), 404 (flag off)

### Hors scope
- Interface admin UI pour consulter les ordres Mock (dev inspecte via DB ou Swagger).
- Persistance longue durée (le Mock peut être purgé régulièrement).
- Simulation de pannes LIMS (délais, erreurs) — hors scope, éventuellement v0.93.

### Définition de Done
- Migration EF appliquée en dev + Synology.
- Feature flag documenté dans `README-DEV.md`.
- Tests xUnit ≥ 95 % coverage sur `MockLimsOrderService` + `MockLimsResultGenerator`.
- Commit avec clé `AQ-32`, push, statut Jira Terminé.

## AQ-33 — Mock LIMS — Outbound : transmission automatique des mandats AquaPlan vers le Mock LIMS

- **Epic parent** : AQ-7
- **Estimation** : M
- **Dépendances** : **AQ-32** (endpoint POST /api/mock-lims/orders consommé)

### User story
**En tant qu'** utilisateur ayant transmis un mandat,
**Je veux** que le mandat soit automatiquement poussé vers le Mock LIMS avec gestion d'idempotence et de retry,
**Afin que** la boucle outbound soit fiable et reproductible, et que je puisse voir l'état de transmission côté mandat.

### Contexte métier
Après clôture d'un mandat (`Completed` → `Transmitted`), AquaPlan doit pousser l'ordre vers le LIMS. Le Mock LIMS (AQ-32) reçoit l'ordre via `POST /api/mock-lims/orders` interne. On introduit un `ILimsClient` abstrait pour isoler le Mock (futur remplacement possible par un vrai LIMS sans changer le service métier). Politique Polly retry exponentiel 3 tentatives (2s, 5s, 15s) avant flag `TransmissionFailed=true`. Idempotence : si `Order.LimsOrderId` déjà renseigné, pas de re-transmission (sauf force). Le retry peut être manuel via un nouveau bouton "Retransmettre" dans l'UI mandat en cas d'échec.

### Critères d'acceptation

**Scénario 1 — Happy path : transmission réussie**
```gherkin
Étant donné un mandat M1 en statut Completed, LimsOrderId=null
Quand le mandataire clique "Transmettre" et l'API POST /api/orders/{M1.Id}/transmit est appelée
Alors ILimsTransmissionService.TransmitAsync est invoqué
Et un POST interne vers /api/mock-lims/orders est émis avec les données du mandat
Et le Mock LIMS retourne 201 Created avec un limsOrderId
Et M1 est mis à jour : Status=Transmitted, LimsOrderId=<guid>, TransmissionFailed=false, TransmittedAt=now
Et un enregistrement audit "OrderTransmitted" est inséré
Et l'API retourne 200 OK avec le DTO mis à jour
```

**Scénario 2 — Edge case : échec LIMS après 3 retry**
```gherkin
Étant donné le Mock LIMS est indisponible (feature flag désactivé ou erreur simulée)
Quand la transmission d'un mandat est déclenchée
Alors Polly tente 3 fois (2s, 5s, 15s) avec backoff exponentiel
Et à la dernière tentative en échec, M1 est mis à jour : TransmissionFailed=true, Status reste Completed
Et l'API retourne 502 Bad Gateway avec { error: "lims.unavailable" }
Et côté UI un badge rouge "Transmission échouée" est affiché sur le mandat
Et un bouton "Retransmettre" permet un retry manuel
```

**Scénario 3 — Permission et idempotence**
```gherkin
Étant donné un mandat M2 déjà transmis (LimsOrderId renseigné)
Quand un utilisateur appelle POST /api/orders/{M2.Id}/transmit
Alors l'API retourne 409 Conflict avec { error: "order.alreadyTransmitted" }
Et aucune nouvelle transmission n'a lieu côté Mock LIMS
Et seul un Admin peut forcer une retransmission via POST /api/orders/{M2.Id}/transmit?force=true
Et un Préleveur recevant 403 Forbidden sur cet endpoint (cas normal : non habilité à transmettre)
```

### Tâches techniques

**Backend — Domain**
- `Order.cs` : ajouter `Guid? LimsOrderId`, `bool TransmissionFailed`, `DateTimeOffset? TransmittedAt`, `int TransmissionAttempts`
- Méthode domaine `MarkAsTransmitted(Guid limsOrderId)` / `MarkTransmissionFailed()`

**Backend — Infrastructure**
- Migration `AddOrderLimsTransmissionFields`
- Index partiel `WHERE transmission_failed = true` pour dashboard admin

**Backend — Application**
- Interface `ILimsClient` :
  - `Task<Guid> SendOrderAsync(LimsOrderPayload payload, CancellationToken ct)`
- Impl `MockLimsClient` (appel HTTP interne vers `/api/mock-lims/orders`)
- Service `ILimsTransmissionService` + impl :
  - `Task TransmitAsync(Guid orderId, bool force, Guid currentUserId)`
  - Polly policy retry 3x exponentiel
  - Mapping Order → LimsOrderPayload

**Backend — API**
- `OrdersController.Transmit` ajouter param `[FromQuery] bool force = false`
- Force réservé Admin (`[Authorize(Roles = "Administrator")]` sur branche force, sinon rôles habituels)
- `[Audited]` conservé

**Frontend**
- `pages/orders/order-detail.component.ts` :
  - Badge rouge "Transmission échouée" si `order.transmissionFailed`
  - Bouton "Retransmettre" (Admin uniquement si déjà transmis, tout user habilité si failed)
- i18n : `orders.transmission.{failed,retry,forceWarning}`
- `datastore/order.datastore.ts` : propager les nouveaux champs

**Tests (obligatoires)**
- `LimsTransmissionServiceTest` :
  - `Transmit_WhenMockSuccess_ShouldUpdateOrderAndReturn`
  - `Transmit_WhenAllRetriesFail_ShouldMarkFailedAndThrow`
  - `Transmit_WhenAlreadyTransmittedWithoutForce_ShouldThrowConflict`
  - `Transmit_WithForceAsAdmin_ShouldProceedAndUpdateLimsOrderId`
- `MockLimsClientTest` :
  - `SendOrder_WithPollyRetry_ShouldSucceedOn2ndAttempt`
  - `SendOrder_AfterMaxRetries_ShouldThrow`
- `OrdersControllerTest` :
  - `Transmit_WithForceAsRequerant_ShouldReturn403`
  - `Transmit_WithoutForceOnTransmittedOrder_ShouldReturn409`

### Hors scope
- Queue persistante en base pour les transmissions échouées (reprise différée).
- Notifications automatiques d'échec (couvert ponctuellement par AQ-44/45 si pertinent).
- Multi-LIMS (un seul client actif).

### Définition de Done
- Transmission Mock opérationnelle en dev localhost + Synology.
- Migration EF appliquée.
- Tests xUnit passants, coverage ≥ 90 % sur `LimsTransmissionService`.
- Commit `AQ-33`, push, Jira Terminé.

## AQ-34 — Mock LIMS — Inbound : réception et persistance des résultats d'analyse

- **Epic parent** : AQ-7
- **Estimation** : L
- **Dépendances** : **AQ-33** (`Order.LimsOrderId` requis pour rattacher les résultats)

### User story
**En tant que** mandataire ou administrateur,
**Je veux** que les résultats d'analyse soient récupérés depuis le Mock LIMS et persistés en base, rattachés à leur mandat d'origine, avec une transition de statut `Transmitted → Done`,
**Afin de** pouvoir consulter les résultats dans AquaPlan sans sortir de l'application.

### Contexte métier
Après transmission (AQ-33), le Mock LIMS expose les résultats via `GET /api/mock-lims/orders/{id}/results` (AQ-32). Côté AquaPlan, on introduit une entité `SamplingResult` (une ligne par paramètre × mandat) avec valeur, unité, seuils de référence, flag de conformité calculé (`value ∈ [min, max]`). Le pull peut être déclenché **manuellement** (endpoint `POST /api/orders/{id}/pull-results`, utile côté support/dev) ou **automatiquement** par le Worker AQ-35. À la réception complète des résultats, le mandat passe `Transmitted → Done`. L'endpoint `GET /api/orders/{id}/results` expose les résultats à l'UI (consommé par AQ-400).

### Critères d'acceptation

**Scénario 1 — Happy path : pull manuel de résultats**
```gherkin
Étant donné un mandat M1 transmis avec LimsOrderId=L1 et 14 paramètres
Et le Mock LIMS a des résultats prêts (statut ResultsReady)
Quand un Admin appelle POST /api/orders/{M1.Id}/pull-results
Alors le service invoque GET /api/mock-lims/orders/L1/results
Et 14 lignes SamplingResult sont insérées en base rattachées à M1.Id
Et chaque ligne contient {parameterCode, value, unit, referenceMin, referenceMax, isConform}
Et le statut de M1 passe à Done, ResultsReceivedAt=now
Et un enregistrement audit "ResultsReceived" est inséré
Et l'API retourne 200 OK avec SamplingResultListDto (count=14)
```

**Scénario 2 — Edge case : résultats pas encore prêts**
```gherkin
Étant donné un mandat M2 transmis mais le Mock LIMS est en statut "Processing" (résultats pas encore prêts)
Quand POST /api/orders/{M2.Id}/pull-results est appelé
Alors l'API retourne 204 No Content (pas d'erreur, juste rien à remonter)
Et M2 reste en statut Transmitted
Et aucune ligne SamplingResult n'est créée
Et un GET /api/orders/{M2.Id}/results retourne une liste vide
```

**Scénario 3 — Permission et idempotence**
```gherkin
Étant donné un mandat M3 avec résultats déjà reçus (Done)
Quand un nouvel appel POST /pull-results est émis
Alors aucune duplication : les 14 lignes existantes sont conservées intactes
Et l'API retourne 200 OK (idempotent)
Et un Préleveur qui n'est pas assigné à M3 appelle GET /api/orders/{M3.Id}/results
Alors l'API retourne 403 Forbidden
Et un accès cross-tenant retourne 404
```

### Tâches techniques

**Backend — Domain**
- Entité `SamplingResult` : `Id, OrderId, ParameterCode, Value (decimal), Unit, ReferenceMin, ReferenceMax, IsConform, MeasuredAt, ReceivedAt`
- Méthode `Order.MarkResultsReceived(DateTimeOffset at)` → transition `Transmitted → Done`

**Backend — Infrastructure**
- Migration `AddSamplingResults` (table + index composite `(order_id, parameter_code)` unique)
- Configuration EF

**Backend — Application**
- Service `ILimsResultService` + impl :
  - `Task<int> PullAsync(Guid orderId, CancellationToken ct)` → nombre de résultats ingérés (0 si pas prêts)
  - Idempotence via check `SamplingResult.Any(r => r.OrderId == orderId)`
- Service `ISamplingResultService.GetByOrderAsync(Guid orderId)` pour UI
- DTOs : `SamplingResultDto`, `SamplingResultListDto(Items, ConformCount, NonConformCount, TotalCount)`

**Backend — API**
- `OrdersController` :
  - `POST /api/orders/{id}/pull-results` → `[Authorize(Roles = "Administrator")]` + `[Audited]` → 200 | 204 | 403 | 404
  - `GET /api/orders/{id}/results` → `[Authorize]` (Admin, Requérant owner, Préleveur assigné) → 200 | 403 | 404

**Tests (obligatoires)**
- `LimsResultServiceTest` :
  - `PullAsync_WhenResultsReady_ShouldInsertAndTransitionToDone`
  - `PullAsync_WhenResultsNotReady_ShouldReturnZero`
  - `PullAsync_WhenAlreadyPulled_ShouldBeIdempotent`
  - `PullAsync_ShouldComputeIsConformCorrectly` (value dans/hors bornes)
- `SamplingResultServiceTest` :
  - `GetByOrder_ShouldReturnOrderedByParameterCode`
  - `GetByOrder_WithNoResults_ShouldReturnEmptyList`
- `OrdersControllerTest` :
  - Attributs HTTP + route + auth + audit
  - 403 Préleveur non assigné, 404 cross-tenant

### Hors scope
- Webhook inbound (push par le Mock) — on reste sur pull only pour simplicité KISS.
- Historisation versionnée des résultats (pas de re-mesure gérée).
- Export des résultats (hors scope, potentiel v0.93 avec AQ-23).

### Définition de Done
- Migration appliquée, tests ≥ 95 % coverage service.
- Endpoints testables via Swagger.
- Commit `AQ-34`, push, Jira Terminé.

## AQ-35 — Mock LIMS — Worker de synchronisation périodique et journal d'audit

- **Epic parent** : AQ-7
- **Estimation** : M
- **Dépendances** : **AQ-34** (consomme `ILimsResultService.PullAsync`)

### User story
**En tant qu'** administrateur,
**Je veux** qu'un worker en arrière-plan pull automatiquement les résultats disponibles toutes les 5 minutes et trace chaque tentative dans un journal d'audit,
**Afin de** garantir la réception automatique des résultats sans intervention manuelle et d'avoir une traçabilité opérationnelle.

### Contexte métier
Le pull manuel (AQ-34) est réservé au support/dev. En production, un `BackgroundService` dans `AquaPlan.Worker` doit scanner périodiquement les mandats `Transmitted` et tenter de pull leurs résultats. Période configurable (défaut 5 min, par `appsettings.json`). Chaque tentative (succès, no-content, erreur) est journalisée dans `lims_sync_logs` pour audit et diagnostic. Le worker doit être robuste : jamais crasher, backoff en cas d'erreur répétée, endpoints admin de consultation du statut et des logs.

### Critères d'acceptation

**Scénario 1 — Happy path : cycle de synchronisation**
```gherkin
Étant donné 3 mandats M1, M2, M3 en statut Transmitted
Et le Mock LIMS retourne des résultats prêts pour M1 et M2 mais pas M3
Quand le LimsSyncWorker exécute un cycle
Alors il scanne les mandats Transmitted
Et appelle PullAsync pour chacun
Et M1 et M2 passent à Done avec leurs résultats persistés
Et M3 reste Transmitted (résultats pas prêts)
Et 3 entrées sont insérées dans lims_sync_logs : 2 succès, 1 skipped
Et le cycle suivant démarre 5 min plus tard
```

**Scénario 2 — Edge case : erreur LIMS n'arrête pas le worker**
```gherkin
Étant donné le Mock LIMS est momentanément indisponible (exception HTTP)
Quand LimsSyncWorker tente un pull
Alors l'exception est catchée, loggée via Serilog
Et une entrée lims_sync_logs est créée avec status=Error, errorMessage
Et le worker continue son cycle normalement (pas de crash du BackgroundService)
Et après 3 cycles consécutifs en erreur, un log WARN est émis (diagnostic)
Et le cycle suivant retentera au bout de la période configurée
```

**Scénario 3 — Permission : endpoints admin de monitoring**
```gherkin
Étant donné un Admin authentifié
Quand il appelle GET /api/admin/lims-sync/status
Alors il reçoit 200 OK avec { isRunning, lastCycleAt, nextCycleAt, pendingOrdersCount, recentLogsCount }
Et quand il appelle GET /api/admin/lims-sync/logs?take=50
Alors il reçoit 200 OK avec les 50 dernières entrées (status, orderId, message, createdAt)
Et un non-Admin reçoit 403 Forbidden sur les 2 endpoints
Et un utilisateur non authentifié reçoit 401
```

### Tâches techniques

**Backend — Domain**
- Entité `LimsSyncLog` : `Id, CycleId (guid), OrderId (nullable), Status (enum: Success, NoContent, Error), Message, StartedAt, CompletedAt, DurationMs`

**Backend — Infrastructure**
- Migration `AddLimsSyncLogs` + index `createdAt DESC`
- Configuration EF

Cela crée 2 notifications si résultats non-conformes (une "ResultsReceived" normale + une "NonConformResult" urgente) — c'est redondant mais volontaire (visibilité maximale). Cette story ajoute uniquement le trigger et la distinction UI urgente, le socle est porté par AQ-43.

### Critères d'acceptation

**Scénario 1 — Happy path : résultat non conforme déclenche alerte urgente**
```gherkin
Étant donné un mandat M1 dont le pull ramène 3 paramètres non conformes sur 14
Quand LimsResultService.PullAsync complète le pull
Alors pour chaque destinataire (Requérant + Admins) sont créées 2 notifications :
  - Une Notification normale Type=ResultsReceived (via AQ-44)
  - Une Notification urgente Type=NonConformResult, IsUrgent=true, Title="⚠ Résultats non conformes", Message="Mandat 'Fontaine Centre' — 3 paramètres non conformes détectés"
Et côté UI la bell affiche "X" unread, dont le badge prend teinte orange vif si ≥1 urgent
Et dans le dropdown, la notification urgente apparaît en tête avec fond rouge
Et un clic redirige vers /orders/M1.Id avec tab Résultats
```

**Scénario 2 — Edge case : tous les résultats conformes**
```gherkin
Étant donné un mandat M2 avec 14 résultats tous conformes
Quand le pull complète
Alors seule la notification AQ-44 "ResultsReceived" est créée
Et AUCUNE notification "NonConformResult" n'est générée
Et le badge bell reste en teinte normale (pas d'alerte urgente)
```

**Scénario 3 — Permission et isolation**
```gherkin
Étant donné un mandat M3 avec non-conformité dans le distributeur D1
Et un Requérant R2 du distributeur D2
Quand les résultats sont reçus
Alors R2 ne reçoit aucune notification non-conforme (périmètre distributeur)
Et le Requérant R1 (owner de M3) et tous les Admins reçoivent la notif urgente
Et un clic sur la notification urgente par un utilisateur non autorisé (cas impossible mais test défensif) retourne 403 si il tente d'ouvrir l'ordre
```

### Tâches techniques

**Backend — Domain**
- `Notification` : ajouter `bool IsUrgent` (default false) — migration `AddNotificationIsUrgent`

**Backend — Application**

## AQ-275 — Permissions profils d'analyse — lecture seule pour non-admin + finitions permissions sensibles

- **Epic parent** : AQ-6 Epic 2.3 Traitement des prélèvements
- **Estimation** : S
- **Dépendances** : aucune (quick-win indépendant, Sprint 1)

### User story
**En tant qu'** administrateur,
**Je veux** que les profils d'analyse soient en lecture seule pour les utilisateurs non-Admin, avec formulaire grisé et actions masquées côté UI + backend qui retourne 403 sur toute tentative d'écriture,
**Afin de** garantir que seul un Admin peut modifier le catalogue d'analyses (données de référence sensibles, impact multi-mandats).

### Contexte métier
Dette originellement ciblée v0.7.1 mais non livrée. Depuis, plusieurs fix permissions ont été faits en v0.9/v0.91 (distributeur, délégations, round lock) mais **les profils d'analyse restent ouverts en écriture à des rôles non-Admin**. Risque : un Requérant ou un Préleveur peut modifier un profil d'analyse → impact sur tous les mandats utilisant ce profil → incohérences. La correction comprend :
1. **Verrouillage backend** : endpoints `POST /api/analysis-profiles`, `PUT /api/analysis-profiles/{id}`, `DELETE /api/analysis-profiles/{id}` passent en `[Authorize(Roles = "Administrator")]` stricte
2. **Lecture seule UI** : formulaire de détail grisé (`[disabled]="!isAdmin"`), boutons "Modifier" / "Supprimer" / "Ajouter un paramètre" masqués
3. **Revue des endpoints sensibles** : audit rapide de `AnalysisProgramsController`, `ContainersController`, `SamplingLocationsController` pour confirmer cohérence permissions

### Critères d'acceptation

**Scénario 1 — Happy path : Admin a accès plein**
```gherkin
Étant donné un Admin authentifié
Quand il ouvre un profil d'analyse existant dans l'UI
Alors le formulaire est éditable (champs actifs)
Et les boutons "Modifier", "Supprimer", "Ajouter un paramètre" sont visibles et cliquables
Et un PUT /api/analysis-profiles/{id} aboutit en 200 OK
Et un POST /api/analysis-profiles aboutit en 201 Created
Et un DELETE aboutit en 204
```

**Scénario 2 — Edge case : non-Admin en consultation**
```gherkin
Étant donné un Requérant ou un Préleveur authentifié
Quand il ouvre un profil d'analyse
Alors le formulaire est en mode read-only (tous les champs grisés via [disabled]="true")
Et les boutons "Modifier", "Supprimer", "Ajouter un paramètre" sont invisibles
Et un appel forgé PUT /api/analysis-profiles/{id} retourne 403 Forbidden
Et un POST retourne 403
Et un DELETE retourne 403
Et la consultation (GET) reste autorisée
```

**Scénario 3 — Audit des autres endpoints sensibles**
```gherkin
Étant donné un Requérant ou un Préleveur
Quand il appelle :
  - DELETE /api/analysis-programs/{id} — doit être Admin only
  - DELETE /api/containers/{id} — doit être Admin only
  - POST /api/sampling-locations (création de LDP sans workflow validation) — doit être Admin only
Alors chaque appel retourne 403 Forbidden
Et la revue identifie les endpoints sensibles manquants et les ajoute au ticket
Et un Admin peut exécuter ces opérations (200/201/204 selon le verbe)
```

### Tâches techniques

**Backend**
- `AnalysisProfilesController` :
  - `[HttpPost]`, `[HttpPut]`, `[HttpDelete]` → `[Authorize(Roles = "Administrator")]`
  - `[HttpGet]` reste `[Authorize]` (lecture ouverte)
- Audit des controllers suivants pour cohérence (compléter si écriture non restreinte) :
  - `AnalysisProgramsController`
  - `ContainersController`
  - `ParametersController` (si existant)
  - `SamplingLocationsController` : créations hors workflow validation doivent être Admin only
- Documenter dans `docs/security/permissions-matrix.md` (ou section README) la matrice rôle × endpoint

**Frontend**
- `pages/analysis-profiles/analysis-profile-detail.component.ts` :
  - Signal `isAdmin = computed(() => this.authService.isInRole('Administrator'))`
  - Template : `<form [disabled]="!isAdmin()">` + `@if (isAdmin()) { <button>Modifier</button> <button>Supprimer</button> }`
- `pages/analysis-profiles/analysis-profile-list.component.ts` : bouton "Nouveau profil" visible uniquement Admin
- Même logique sur `analysis-programs`, `containers` (audit UI parallèle)
- i18n : clé `common.readOnlyMode` (fr="Lecture seule", de="Schreibgeschützt", en="Read only")

**Tests (obligatoires)**
- `AnalysisProfilesControllerTest` :
  - `Post_AsRequerant_ShouldReturn403`
  - `Put_AsPreleveur_ShouldReturn403`
  - `Delete_AsRequerant_ShouldReturn403`
  - `Get_AsRequerant_ShouldReturn200` (lecture OK)
  - Attributs `[Authorize(Roles = "Administrator")]` testés explicitement
- `AnalysisProgramsControllerTest` : symétrique
- `ContainersControllerTest` : symétrique
- `SamplingLocationsControllerTest` : vérifier endpoint POST pour création directe

### Hors scope
- Rôle custom "Catalogue Manager" (entre Admin et Requérant) — hors scope, overkill.
- UI de gestion des rôles utilisateurs.
- Audit complet de sécurité (on cible uniquement les endpoints du catalogue).

### Définition de Done
- Tests passants (unitaires + attributs controller).
- UI grisée pour non-Admin (captures d'écran avant/après en commentaire Jira).
- Matrice permissions documentée.
- Commit `AQ-275`, push, Jira Terminé.

## AQ-86 — Optimisation responsive / tablette pour préleveurs terrain (iPad 768–1024px)

- **Epic parent** : AQ-13 Epic 4.4 Optimisations
- **Estimation** : M
- **Dépendances** : aucune (indépendant, Sprint 1 en parallèle)

### User story
**En tant que** préleveur terrain utilisant un iPad,
**Je veux** que les écrans principaux (détail tournée, saisie prélèvement, scan barcode) soient optimisés pour une utilisation tactile sur iPad (breakpoints 768–1024px, portrait et paysage),
**Afin d'** être productif sur le terrain sans avoir à zoomer ou à basculer en vue desktop.

### Contexte métier
La v0.916 (PWA offline) a partiellement adapté la consultation mobile. Cette story **finalise** l'expérience tablette iPad, appareil réellement utilisé par les préleveurs. Scope ciblé sur les écrans **critiques terrain** :
- `sampling-round-detail.component.ts` : liste des mandats de la tournée, accès rapide saisie
- `sampling-form-dialog.component.ts` : formulaire de saisie d'un prélèvement (codes-barres, LDP de substitution, conditions environnementales)
- `barcode-scanner.component.ts` (v0.9 AQ-345) : interface caméra pleine largeur tablette
- `order-detail.component.ts` : consultation mandat terrain
- `home.component.ts` : dashboard (cohérence AQ-31 tuiles)

Breakpoints : Bootstrap 5 `md` (≥768px) + `lg` (≥992px). Cibles : iPad Mini (768×1024), iPad Air (820×1180), iPad Pro 11" (834×1194). Tailles de boutons ≥ 44×44 px (Apple HIG), espaces tactiles respectés, pas de hover-only (tous actions accessibles en tap).

### Critères d'acceptation

**Scénario 1 — Happy path : saisie sur iPad portrait**
```gherkin
Étant donné un préleveur sur iPad Air en mode portrait (820×1180)
Quand il ouvre sampling-round-detail pour sa tournée T1 avec 15 mandats
Alors la liste mandats affiche 1 colonne en pleine largeur (pas de scroll horizontal)
Et chaque ligne mandat a une hauteur ≥ 64px avec boutons ≥ 44×44px
Et un tap sur un mandat ouvre directement l'écran de saisie (pas d'étape intermédiaire)
Et la modale sampling-form-dialog occupe 90% de la largeur (confortable) avec champs empilés verticalement
Et le clavier virtuel qui apparaît ne masque pas les champs actifs (scroll automatique)
```

**Scénario 2 — Edge case : rotation paysage et scanner barcode**
```gherkin
Étant donné le préleveur passe l'iPad en mode paysage (1180×820) pendant la saisie
Quand il rotate l'appareil
Alors le layout se réorganise : formulaire en 2 colonnes (champs courts + boutons à droite)
Et aucun composant n'est coupé ou overlappé
Et quand il active le scanner barcode
Alors la vue caméra prend toute la largeur utile (respecte ratio 16:9 ou 4:3)
Et le bouton "Valider" du scan reste accessible sans scroll
```

**Scénario 3 — Permission / accessibilité tactile**
```gherkin
Étant donné tous les rôles utilisent l'app sur iPad
Quand ils interagissent en mode tactile
Alors aucun élément interactif ne repose sur hover uniquement (ex. tooltips ont alternative tap)
Et les boutons primaires sont tous ≥ 44×44px (Apple HIG)
Et les zones de tap sur éléments de liste font au moins 48×48px (Material Design touch target)
Et les formulaires utilisent des inputs avec keyboard hints (inputmode="numeric" pour chiffres, "email" pour email)
Et le contraste WCAG AA est respecté (check via Lighthouse mobile)
```

### Tâches techniques

**Frontend — Audit et adaptations**
- Audit Lighthouse Mobile sur les 5 écrans cibles (sampling-round-detail, sampling-form-dialog, barcode-scanner, order-detail, home)
- Relevé des issues : éléments coupés, boutons trop petits, scroll horizontal, hover-only
- Corrections SCSS via media queries Bootstrap :
  ```scss
  @media (min-width: 768px) and (max-width: 1199px) {
    // tablet-specific styles
    .btn { min-height: 44px; min-width: 44px; }
    .list-item { min-height: 64px; padding: 12px 16px; }
    .mat-dialog-container { max-width: 90vw; }
  }
  ```
- Ajout classes utilitaires `.tablet-stack` (empilage vertical forcé), `.tablet-grid-2` (grille 2 colonnes)
- Composant `<mat-dialog>` sampling-form-dialog : configurer `maxWidth: '90vw'`, `width: '800px'` en tablette

**Frontend — Inputs**
- Ajouter `inputmode` / `autocomplete` appropriés sur tous les inputs de saisie terrain :
  - Codes-barres : `inputmode="numeric"` ou `inputmode="tel"`
  - Températures : `inputmode="decimal"`
  - Notes textuelles : `inputmode="text"`
- `<input>` avec `type="search"` pour filtres (clavier iOS avec bouton search)

**Frontend — Scanner caméra**
- `barcode-scanner.component.ts` : ajuster CSS pour ratio caméra pleine largeur tablette
- Bouton "Annuler" en haut à droite (zone pouce facile)
- Bouton "Valider scan" en bas, pleine largeur en mobile/tablette

**Frontend — Tests manuels**
- Tests dans Chrome DevTools : device simulation iPad Mini / Air / Pro
- Tests réels sur un iPad physique (fourni par l'utilisateur ou via Synology access)
- Vérifier navigation clavier virtuel (focus sur champ → clavier apparaît → champ reste visible)
- Capture d'écran avant/après pour chaque écran cible en commentaire Jira

**Backend** : aucun changement nécessaire.

**Tests**
- Non-régression manuelle exhaustive sur iPad (au moins un modèle)
- Non-régression desktop pour confirmer l'absence de régression (breakpoint `lg+` inchangé)
- Pas de tests Angular unitaires (convention)
- Pas de tests xUnit backend (hors scope frontend uniquement)

### Hors scope
- Téléphones mobiles < 768px (déjà partiellement traité v0.916, pas retouché ici).
- Mode très large 2560×1440 (écrans desktop haute résolution) — hors scope.
- Application native iOS (SwiftUI) — non pertinent, on reste PWA.
- Tests automatisés responsive (Lighthouse CI) — à prévoir v0.93.

### Définition de Done
- 5 écrans cibles validés sur iPad réel (ou simulateur Chrome fidèle).
- Captures d'écran avant/après jointes en commentaire Jira.
- Aucune régression desktop.
- Validation UX Lead rapide avant clôture.
- Commit `AQ-86`, push, Jira Terminé.
