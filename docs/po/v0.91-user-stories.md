## 091-01 — Création mandat/tournée restreinte au distributeur autorisé

- **Epic parent** : Epic F Bugfix autorisation distributeur
- **Estimation** : M
- **Dépendances** : aucune (démarrage immédiat Sprint 1, bloque la suite offline car le lock s'applique au niveau tournée)

### User story
**En tant que** Requérant ou Requérant-Préleveur,
**Je veux** que la création d'un mandat ou d'une tournée soit restreinte au distributeur auquel je suis rattaché **et** aux distributeurs qui m'ont délégué l'autorité via une `DistributorDelegation` active,
**Afin d'** empêcher toute création sur un périmètre pour lequel je n'ai pas l'autorité et d'obtenir un dropdown correctement filtré dans les dialogs de création.

### Contexte métier
Post AQ-365, la création a été restreinte aux rôles Admin + Requérant + Requérant-Préleveur. Mais la règle distributeur n'est pas appliquée : un Requérant peut actuellement choisir n'importe quel distributeur du tenant dans le dropdown et créer un mandat hors de son périmètre. Le mécanisme de délégation distributeur (`DistributorDelegation`) existe déjà en base pour permettre à un distributeur A de déléguer temporairement la saisie à un utilisateur du distributeur B. La règle à appliquer : un utilisateur non-Admin ne peut créer que sur `user.distributorId` + tout `DelegatedToDistributorId = user.distributorId` actif (`IsActive=true` ET `ValidFrom ≤ now ≤ ValidTo ou ValidTo null`). Admin n'est pas restreint.

### Critères d'acceptation

**Scénario 1 — Happy path : Requérant avec une délégation active**
```gherkin
Étant donné un Requérant U1 rattaché au distributeur D1
Et une DistributorDelegation active où DelegatingDistributorId=D2, DelegatedToDistributorId=D1, IsActive=true, ValidFrom ≤ now ≤ ValidTo
Quand U1 ouvre le dialog de création de mandat
Alors le dropdown distributeur propose uniquement {D1, D2}
Et la création d'un mandat avec distributorId=D1 aboutit en 201 Created
Et la création d'un mandat avec distributorId=D2 aboutit aussi en 201 Created
```

**Scénario 2 — Edge case : délégation expirée ou inactive**
```gherkin
Étant donné un Requérant U1 rattaché à D1
Et une DistributorDelegation D2→D1 avec ValidTo dans le passé (expirée)
Et une autre DistributorDelegation D3→D1 avec IsActive=false (désactivée manuellement)
Quand U1 ouvre le dialog de création de tournée
Alors le dropdown distributeur propose uniquement {D1}
Et un appel forgé POST /api/sampling-rounds avec distributorId=D2 ou D3 retourne 403 Forbidden
Et le message d'erreur précise "Vous n'êtes pas autorisé sur ce distributeur"
```

**Scénario 3 — Permission : Admin non restreint + isolation tenant**
```gherkin
Étant donné un Admin connecté au tenant T1 avec 5 distributeurs en base
Quand il ouvre le dialog de création de mandat
Alors le dropdown propose les 5 distributeurs de T1
Et la création sur n'importe lequel aboutit en 201 Created
Et un Admin du tenant T2 ne voit jamais les distributeurs de T1 (isolation tenant globale préservée)
Et un Préleveur (non-Requérant) reçoit 403 Forbidden au POST — inchangé vs AQ-365
```

### Tâches techniques

**Backend — Application**
- `IDelegationService` : nouvelle méthode `Task<IReadOnlyList<Guid>> GetAuthorizedDistributorIdsForUserAsync(Guid userId, CancellationToken ct)`
  - Retour : `[user.DistributorId]` + tous `DelegatingDistributorId` des `DistributorDelegation` où `DelegatedToDistributorId=user.DistributorId` ET `IsActive=true` ET `ValidFrom ≤ now` ET (`ValidTo IS NULL OR ValidTo ≥ now`)
  - Admin : méthode retourne `null` (signal "pas de restriction") OU bypass côté caller via `authService.IsInRole("Administrator")`
- `OrderService.CreateAsync` : avant persistance, si user non-Admin, vérifier `dto.DistributorId ∈ GetAuthorizedDistributorIdsForUserAsync(currentUserId)` ; sinon `throw ForbiddenException("Distributor not authorized for current user")`
- `SamplingRoundService.CreateAsync` : idem

**Backend — API**
- Nouveau endpoint `GET /api/delegations/my-authorized-distributors`
  - `[HttpGet("my-authorized-distributors")]`
  - `[Authorize]`
  - Retour 200 `IList<DistributorDto>` — filtré par `GetAuthorizedDistributorIdsForUserAsync`
  - Admin : retourne **tous** les distributeurs du tenant
- `ApiExceptionFilterAttribute` : mapper `ForbiddenException` → 403 Forbidden avec body `{ error: "distributor.notAuthorized" }`

**Frontend**
- `pages/orders/order-form-dialog.component.ts` et `pages/sampling-rounds/sampling-round-form-dialog.component.ts` :
  - Au lieu d'appeler `GET /api/distributors` pour le dropdown, appeler `GET /api/delegations/my-authorized-distributors`
  - Conserver fallback si 403 → toast clair "Aucun distributeur autorisé, contactez un administrateur"
- `datastore/distributor.datastore.ts` : nouveau signal `authorizedDistributors` + méthode `loadAuthorized()`
- Clés i18n `orders.create.errors.distributorNotAuthorized` / `samplingRounds.create.errors.distributorNotAuthorized` (fr/de/en)

**Tests (obligatoires)**
- `DelegationServiceTest` :
  - `GetAuthorizedDistributorIdsForUser_WithOwnDistributorOnly_ShouldReturnSingle`
  - `GetAuthorizedDistributorIdsForUser_WithActiveDelegation_ShouldIncludeDelegator`
  - `GetAuthorizedDistributorIdsForUser_WithExpiredDelegation_ShouldExcludeDelegator`
  - `GetAuthorizedDistributorIdsForUser_WithInactiveDelegation_ShouldExcludeDelegator`
- `OrderServiceTest` :
  - `Create_WithUnauthorizedDistributor_ShouldThrowForbidden`
  - `Create_WithDelegatedDistributor_ShouldSucceed`
  - `Create_AsAdmin_WithAnyDistributor_ShouldSucceed`
- `SamplingRoundServiceTest` : symétrique
- `DelegationsControllerTest` / `OrdersControllerTest` / `SamplingRoundsControllerTest` : attributs HTTP + rôle, 401, 403 cross-distributor

## 091-02 — Transition Assigned → InProgress : ping réseau + pose du lock

- **Epic parent** : Epic G Checkout tournée + offline
- **Estimation** : M
- **Dépendances** : aucune côté backend ; couplée à **091-03** (effet du lock) et **091-04** (force-unlock)

### User story
**En tant que** Préleveur,
**Je veux** qu'au démarrage de ma tournée (transition `Assigned → InProgress`), l'application vérifie d'abord la connexion réseau et, en cas de succès, pose un verrou sur la tournée et tous ses mandats,
**Afin que** le serveur et le mandataire sachent que je suis en train d'opérer la tournée hors ligne et que les données seront cohérentes à la fin de la synchro.

### Contexte métier
Le mode hors ligne repose sur une règle simple : une seule tournée active par préleveur, téléchargée entièrement au démarrage, travaillée offline, synchronisée au retour. Pour garantir la cohérence, personne d'autre que le préleveur (hors Admin, pour le force-unlock) ne peut modifier la tournée tant qu'elle est `InProgress`. Le démarrage **exige** le réseau (impossible de démarrer offline puisqu'il faut télécharger le snapshot). Le lock est matérialisé par trois colonnes ajoutées à `sampling_rounds` ; les mandats associés héritent du lock via la tournée parente (pas de duplication colonne sur `orders` — décision KISS).

### Critères d'acceptation

**Scénario 1 — Happy path : démarrage online avec pose du lock**
```gherkin
Étant donné une tournée T1 en statut Assigned assignée au préleveur U1
Quand U1 clique sur "Démarrer la tournée"
Et qu'un ping GET /api/health répond 200 en < 3s
Alors l'API PATCH /api/sampling-rounds/{T1.Id}/start est appelée
Et la tournée passe en InProgress
Et en base : IsLocked=true, LockedById=U1.Id, LockedAt=now
Et le snapshot (091-05) est téléchargé immédiatement après
Et un enregistrement audit "RoundStarted" est inséré
```

**Scénario 2 — Edge case : pas de réseau au démarrage**
```gherkin
Étant donné le préleveur U1 est hors ligne (Wi-Fi coupé, ping GET /api/health échoue avec timeout 3s)
Quand U1 clique sur "Démarrer la tournée"
Alors un toast rouge s'affiche "Connexion requise pour démarrer la tournée"
Et aucune requête PATCH /start n'est émise
Et la tournée reste en statut Assigned
Et aucun lock n'est posé
```

**Scénario 3 — Permission : tournée non assignée à l'utilisateur**
```gherkin
Étant donné une tournée T2 assignée au préleveur U2
Quand le préleveur U1 tente PATCH /api/sampling-rounds/{T2.Id}/start
Alors l'API retourne 403 Forbidden
Et aucune modification n'a lieu en base
Et un Admin peut en revanche forcer la transition (cas rare, opérationnel)
```

### Tâches techniques

**Backend — Domain**
- `SamplingRound.cs` : ajouter `bool IsLocked`, `Guid? LockedById`, `DateTimeOffset? LockedAt`
- Méthode domaine `LockForSampling(Guid userId, DateTimeOffset now)` / `Unlock()`

**Backend — Infrastructure**
- Migration `AddRoundLockFields` :
  - `ALTER TABLE sampling_rounds ADD COLUMN is_locked bool NOT NULL DEFAULT false`
  - `ALTER TABLE sampling_rounds ADD COLUMN locked_by_id uuid NULL REFERENCES asp_net_users(id) ON DELETE SET NULL`
  - `ALTER TABLE sampling_rounds ADD COLUMN locked_at timestamptz NULL`
- Index partiel `CREATE INDEX ix_sampling_rounds_locked ON sampling_rounds(locked_by_id) WHERE is_locked = true`

**Backend — Application**
- `ISamplingRoundService.StartAsync(Guid roundId, Guid currentUserId)` :
  - Vérifier tournée `Assigned`, assignée à `currentUserId` (ou Admin)
  - Transition `Assigned → InProgress` + pose du lock
  - Retour `SamplingRoundDetailDto`
- `[Audited]` sur le endpoint

**Backend — API**
- `SamplingRoundsController.Start(Guid id)` :
  - `[HttpPatch("{id:guid}/start")]`
  - `[Authorize(Roles = "Administrator,Preleveur,Requerant-Preleveur")]`
  - `[Audited]`
  - Retour 200 `SamplingRoundDetailDto` | 403 | 404 | 409 si déjà InProgress

**Frontend**
- `components/common/network-check.service.ts` (nouveau, singleton) : `async pingServer(timeoutMs = 3000): Promise<boolean>` → fetch `GET /api/health` avec `AbortController` + timeout
- `pages/sampling-rounds/sampling-round-detail.component.ts` :
  - Bouton "Démarrer la tournée" (visible uniquement si statut=Assigned et user=assignedPreleveur ou Admin)
  - Au clic : `await networkCheck.pingServer()` ; si `false` → toast "Connexion requise" ; sinon → `await api.startRound(id)` → toast succès → déclenche download snapshot (091-05)
- i18n : `samplingRounds.start.{button,requiresNetwork,success,error}`

**Tests (obligatoires)**
- `SamplingRoundServiceTest` :
  - `Start_WhenAssigned_ShouldTransitionAndLock`
  - `Start_WhenNotAssignedToUser_ShouldThrowForbidden`
  - `Start_WhenAlreadyInProgress_ShouldThrowConflict`
  - `Start_ShouldSetLockedByIdAndLockedAt`
- `SamplingRoundsControllerTest` : attributs HTTP/route/auth/audit, 401/403/404/409

## 091-03 — Tournée verrouillée : mandataire bloqué en modification

- **Epic parent** : Epic G Checkout tournée + offline
- **Estimation** : M
- **Dépendances** : **091-02** (lock posé)

### User story
**En tant que** Requérant (mandataire) ou tout utilisateur non-préleveur de la tournée,
**Je veux** être **empêché de modifier** une tournée ou ses mandats tant qu'elle est `InProgress` (verrouillée par le préleveur), avec un message clair expliquant qui l'a verrouillée,
**Afin de** garantir l'intégrité des données pendant le travail terrain et éviter les conflits de synchronisation.

### Contexte métier
Pendant qu'un préleveur travaille offline sur sa tournée, n'importe quelle modification côté mandataire (ajout/retrait de mandat, édition d'un programme, bulk-validate, suppression, etc.) créerait un conflit à la synchro. Option B stricte retenue : **toutes les opérations d'écriture sur la tournée et ses mandats sont bloquées** tant que `IsLocked=true`, sauf pour le préleveur qui détient le lock et pour l'Admin (qui a besoin de pouvoir force-unlock — story 091-04).

### Critères d'acceptation

**Scénario 1 — Happy path : mandataire bloqué avec message**
```gherkin
Étant donné une tournée T1 en statut InProgress verrouillée par le préleveur U1 (nom "Jean Dupont")
Et un Requérant U2 (mandataire du mandat M1 appartenant à T1)
Quand U2 tente PUT /api/orders/{M1.Id} avec des modifications
Alors l'API retourne 409 Conflict
Et le body contient { error: "round.locked", lockedByName: "Jean Dupont", lockedAt: "2026-04-18T10:15:00Z" }
Et aucune modification n'est persistée
Et côté UI : bandeau orange "Tournée verrouillée — en cours par Jean Dupont depuis 10:15" + boutons désactivés
```

**Scénario 2 — Edge case : opérations multiples bloquées**
```gherkin
Étant donné une tournée verrouillée
Quand un mandataire tente tour à tour :
  - PUT /api/orders/{id}
  - DELETE /api/orders/{id}
  - PUT /api/sampling-rounds/{id}
  - POST /api/sampling-rounds/{id}/orders (ajout)
  - DELETE /api/sampling-rounds/{id}/orders/{orderId} (retrait)
  - POST /api/orders/bulk-validate concernant au moins un mandat de la tournée
  - POST /api/orders/bulk-transmit concernant au moins un mandat de la tournée
Alors chaque appel retourne 409 Conflict avec { error: "round.locked", ... }
Et aucune modification en base n'a lieu
Et les actions de lecture (GET) restent autorisées pour consultation
```

**Scénario 3 — Permission : exceptions préleveur et Admin**
```gherkin
Étant donné une tournée T1 verrouillée par le préleveur U1
Quand U1 lui-même tente PUT /api/samplings/{id} pour saisir un prélèvement
Alors l'API retourne 200 OK (le propriétaire du lock peut agir)
Et quand un Admin tente PATCH /api/sampling-rounds/{T1.Id}/force-unlock (091-04)
Alors l'opération aboutit (seul endpoint Admin autorisé à écrire sur une tournée verrouillée autre que le préleveur)
Mais un Admin qui tente PUT /api/orders/{M1.Id} (modif normale) reçoit aussi 409 pour rester cohérent avec la règle "tournée verrouillée"
```

### Tâches techniques

**Backend — Application**
- Nouvelle classe helper `RoundLockGuard` (ou méthode extension `ISamplingRoundService.EnsureNotLockedForWriteAsync(Guid roundId, Guid currentUserId, bool allowAdminForceUnlock = false)`)
  - Si `IsLocked=true` ET `currentUserId != LockedById` → `throw RoundLockedException(lockedByName, lockedAt)`
- Appeler ce guard dans : `OrderService.UpdateAsync`, `OrderService.DeleteAsync`, `OrderService.AddToRoundAsync`, `OrderService.RemoveFromRoundAsync`, `OrderService.BulkValidateAsync`, `OrderService.BulkTransmitAsync`, `SamplingRoundService.UpdateAsync`, `SamplingRoundService.DeleteAsync`
- `RoundLockedException` → mapper via `ApiExceptionFilterAttribute` vers 409 Conflict avec `{ error: "round.locked", lockedByName, lockedAt }`

**Frontend**
- Composant réutilisable `<app-round-lock-banner [round]="round()">` : bandeau orange affiché si `round.isLocked=true` avec nom préleveur et heure
- Dans `sampling-round-detail.component.ts` et `order-detail.component.ts` :
  - Signal `isLocked = computed(() => round()?.isLocked && currentUser().id !== round()?.lockedById)`
  - Désactiver tous les boutons de modification via `[disabled]="isLocked()"`
- Dans `order-list.component.ts` : badge visuel "Verrouillée" sur les lignes dont la tournée parente est locked (via flag DTO ajouté), tooltip avec nom préleveur
- Gestion d'erreur 409 avec `error === "round.locked"` : toast orange au lieu de rouge "Tournée verrouillée par {nom}, réessayez après sa fin"
- i18n : `common.roundLocked.{banner,toast,tooltip}`

**Tests (obligatoires)**
- `OrderServiceTest` :
  - `Update_WhenRoundLocked_ShouldThrowConflict`
  - `Update_WhenRoundLockedByCurrentUser_ShouldSucceed` (préleveur peut agir)
  - `Delete_WhenRoundLocked_ShouldThrowConflict`
  - `BulkValidate_WithAtLeastOneOrderInLockedRound_ShouldThrowConflict`
- `SamplingRoundServiceTest` :
  - `Update_WhenLocked_ShouldThrowConflictEvenForAdmin`
- `ApiExceptionFilterTest` : `RoundLockedException → 409 Conflict` avec payload attendu

## 091-04 — Admin force-unlock via InProgress → Assigned

- **Epic parent** : Epic G Checkout tournée + offline
- **Estimation** : M
- **Dépendances** : **091-02** (lock existe), **091-03** (lock bloque les écritures)

### User story
**En tant qu'** Administrateur,
**Je veux** pouvoir **forcer le déverrouillage** d'une tournée bloquée (préleveur injoignable, appareil perdu, etc.) en la remettant en statut `Assigned`,
**Afin de** débloquer le planning en sachant que le travail offline non synchronisé de ce préleveur sera perdu (comportement option B assumé).

### Contexte métier
Cas exceptionnel mais opérationnellement critique : un préleveur a démarré sa tournée (lock posé), puis son appareil tombe en panne, il part en vacances sans synchroniser, ou il perd la connectivité durablement. Le mandataire ne peut plus travailler ses mandats. L'Admin doit pouvoir réinitialiser la tournée en `Assigned`. Règle : **le travail offline non poussé est abandonné** — quand le préleveur retrouvera le réseau, sa sync queue recevra 409 (la tournée n'est plus locked par lui) et un toast lui expliquera.

### Critères d'acceptation

**Scénario 1 — Happy path : Admin déverrouille**
```gherkin
Étant donné une tournée T1 en statut InProgress verrouillée par U1 depuis 3 heures
Et un Admin connecté
Quand il appelle POST /api/sampling-rounds/{T1.Id}/force-unlock
Alors la tournée repasse en statut Assigned
Et en base : IsLocked=false, LockedById=null, LockedAt=null
Et un enregistrement audit_log "RoundForceUnlocked" est inséré {byAdminId, targetRoundId, previousLockedById, timestamp}
Et la réponse est 200 OK avec le DTO mis à jour
```

**Scénario 2 — Edge case : préleveur revient en ligne après force-unlock**
```gherkin
Étant donné la tournée T1 a été force-unlock par Admin à 14:00
Et le préleveur U1 était hors ligne et a continué à saisir des prélèvements locaux
Quand à 15:30, U1 retrouve le réseau et sa sync queue tente de pousser ses actions
Alors la première requête (ex. PUT /api/samplings/{id}) retourne 409 Conflict avec { error: "round.unlocked" }
Et le SyncService détecte ce code → purge la queue + clearSnapshot(T1.Id)
Et U1 voit un toast rouge persistant "Votre tournée a été réinitialisée par un administrateur. Les saisies non synchronisées sont perdues."
```

**Scénario 3 — Permission : Admin only**
```gherkin
Étant donné une tournée verrouillée
Quand un Requérant ou un Préleveur (autre que celui qui détient le lock) appelle POST /force-unlock
Alors l'API retourne 403 Forbidden
Et même le préleveur qui détient le lock ne peut pas s'auto-unlock via cet endpoint (il termine la tournée via le workflow normal Complete)
Et un appel non authentifié retourne 401 Unauthorized
```

### Tâches techniques

**Backend — Application**
- `ISamplingRoundService.ForceUnlockAsync(Guid roundId, Guid adminUserId)` :
  - Vérifier `IsLocked=true` et statut `InProgress` — sinon 409 "round.notLocked"
  - Transition `InProgress → Assigned`
  - Reset `IsLocked=false, LockedById=null, LockedAt=null`
  - Audit log "RoundForceUnlocked"

**Backend — API**
- `SamplingRoundsController.ForceUnlock(Guid id)` :
  - `[HttpPost("{id:guid}/force-unlock")]`
  - `[Authorize(Roles = "Administrator")]`
  - `[Audited]`
  - Retour 200 `SamplingRoundDetailDto` | 403 | 404 | 409

**Frontend**
- `pages/sampling-rounds/sampling-round-detail.component.ts` :
  - Si Admin + `round.isLocked` : afficher bouton "Déverrouiller (force)" rouge, avec confirmation modale listant les conséquences ("Le travail non synchronisé du préleveur {nom} sera perdu. Confirmer ?")
  - Appel `api.forceUnlockRound(id)` → toast vert succès → refresh vue
- i18n : `samplingRounds.forceUnlock.{button,confirmTitle,confirmBody,success,error}`

**Tests (obligatoires)**
- `SamplingRoundServiceTest` :
  - `ForceUnlock_WhenLocked_ShouldTransitionToAssignedAndClearLock`
  - `ForceUnlock_WhenNotLocked_ShouldThrowConflict`
  - `ForceUnlock_ShouldWriteAuditLog`
- `SamplingRoundsControllerTest` : attributs HTTP/route/auth/audit, 401, 403 (non-admin), 404, 409

## 091-05 — Endpoint offline-snapshot complet

- **Epic parent** : Epic G Checkout tournée + offline
- **Estimation** : L
- **Dépendances** : **091-02** (snapshot téléchargé juste après le start) — techniquement indépendant mais fonctionnellement couplé

### User story
**En tant que** Préleveur,
**Je veux** qu'au démarrage de ma tournée, l'application télécharge en une seule requête l'**intégralité des données** dont j'ai besoin pour travailler hors ligne (mandats, programmes, profils, contenants, LDP actifs, prélèvements existants),
**Afin de** pouvoir exécuter tous les prélèvements et remplacer un LDP sans réseau.

### Contexte métier
Le mode offline exige que toutes les données nécessaires soient disponibles localement. Un préleveur peut avoir besoin de : consulter les détails du mandat, voir les contenants requis, saisir un code-barres, remplacer un LDP (ex. accès interdit à un point → bascule sur un LDP alternatif du même distributeur). Un appel unique agrégé simplifie le code frontend, la stratégie de cache, et réduit la surface d'échec. Cible de perf : < 2s même avec 50 mandats et ~200 LDP. Endpoint en **lecture seule** — il ne touche jamais à l'état de la tournée.

### Critères d'acceptation

**Scénario 1 — Happy path : snapshot complet pour une tournée de 10 mandats**
```gherkin
Étant donné une tournée T1 InProgress assignée au préleveur U1
Et T1 contient 10 mandats avec 3 programmes, 15 profils, 5 contenants distincts
Et le distributeur de T1 compte 80 LDP actifs validés
Quand U1 appelle GET /api/sampling-rounds/{T1.Id}/offline-snapshot
Alors la réponse est 200 OK avec un DTO contenant :
  - round: SamplingRoundDetailDto complet
  - orders: 10 OrderDetailDto avec leurs programmes et contenants requis dédupliqués
  - samplingLocations: 80 SamplingLocationDto (tous les LDP actifs+validés du distributeur de T1)
  - analysisPrograms: tous les programmes référencés
  - analysisProfiles: tous les profils référencés
  - containers: tous les contenants distincts référencés
  - samplings: tous les samplings existants de T1 avec leurs sampling_containers
Et le temps de réponse p95 < 2s
Et aucune modification de données n'a lieu
```

## 091-07 — IndexedDB : snapshot actif + file d'actions

- **Epic parent** : Epic G Checkout tournée + offline
- **Estimation** : L
- **Dépendances** : **091-05** (format snapshot) et **091-06** (contexte PWA)

### User story
**En tant que** Préleveur,
**Je veux** que l'application stocke mon snapshot de tournée et mes actions non synchronisées dans une base **IndexedDB** robuste côté navigateur,
**Afin de** conserver mes saisies même si je ferme l'onglet ou redémarre la tablette avant le retour en ligne.

### Contexte métier
Le cache Service Worker ne suffit pas pour un mode offline robuste : il cache les réponses GET mais ne stocke pas les actions pending en attente de replay. IndexedDB, via la lib `idb` (wrapper promise-based), offre une API simple et un stockage persistant. Deux object stores : `active-round` (un seul snapshot à la fois, clé = roundId) et `pending-actions` (file ordonnée FIFO). Le service Angular `OfflineStorageService` expose une API propre sans exposer IndexedDB aux consommateurs.

### Critères d'acceptation

**Scénario 1 — Happy path : sauvegarde et lecture du snapshot**
```gherkin
Étant donné le préleveur démarre la tournée T1 (online)
Et le snapshot offline est téléchargé
Quand OfflineStorageService.saveSnapshot(snapshot) est appelé
Alors la base IndexedDB "aquaplan-offline" existe avec object store "active-round"
Et une entrée { roundId: T1.Id, data: { ... }, savedAt: now } est persistée
Et une lecture ultérieure OfflineStorageService.getSnapshot(T1.Id) retourne les mêmes données
Et clearSnapshot(T1.Id) supprime l'entrée
```

**Scénario 2 — Edge case : queue d'actions FIFO**
```gherkin
Étant donné le préleveur saisit offline 3 prélèvements A, B, C
Quand OfflineStorageService.queueAction({ type: 'UPDATE_SAMPLING', ... }) est appelé 3 fois
Alors 3 entrées sont créées dans l'object store "pending-actions" avec actionId auto-incrémenté (1, 2, 3)
Et getPendingActions() retourne les 3 actions dans l'ordre d'insertion
Et removeAction(1) retire la première ; getPendingActions() retourne alors [2, 3]
Et les données persistent après fermeture/réouverture de l'onglet
```

**Scénario 3 — Permission / isolation logique**
```gherkin
Étant donné un utilisateur U1 se déconnecte de l'app
Quand un autre utilisateur U2 se connecte sur le même appareil
Alors le snapshot de U1 ne doit PAS être lisible par U2 côté UI
Et le SyncService doit purger l'IndexedDB au logout (clear complet)
Et en cas d'erreur d'accès IndexedDB (mode privé Safari, quota dépassé), un toast d'erreur explicite s'affiche
Et le mode offline est considéré indisponible pour la session
```

### Tâches techniques

**Frontend — Dépendance**
- `npm install idb` (wrapper promise-based IndexedDB, ~1kB gzip)

**Frontend — Service**
- `services/offline-storage.service.ts` :
  ```ts
  @Injectable({ providedIn: 'root' })
  export class OfflineStorageService {
    private dbPromise = openDB('aquaplan-offline', 1, { upgrade(db) { ... } });
    saveSnapshot(snapshot: OfflineSnapshotDto): Promise<void>;
    getSnapshot(roundId: string): Promise<OfflineSnapshotDto | undefined>;
    clearSnapshot(roundId: string): Promise<void>;
    queueAction(action: PendingAction): Promise<number>;
    getPendingActions(): Promise<PendingAction[]>;
    removeAction(actionId: number): Promise<void>;
    clearAll(): Promise<void>;
  }
  ```
- Object stores :
  - `active-round` keyPath=`roundId`
  - `pending-actions` keyPath=`actionId` autoIncrement + index `createdAt`
- Type `PendingAction { actionId?: number; type: 'UPDATE_SAMPLING' | 'CREATE_SAMPLING' | ...; payload: unknown; createdAt: string; retries: number; }`

**Frontend — Intégration cycle de vie**
- `auth.service.ts` au logout : `await offlineStorage.clearAll()`
- Gestion erreurs : try/catch avec fallback gracieux + toast

**Tests**
- Non-régression manuelle :
  - Fermer/rouvrir onglet : snapshot persiste
  - Logout : données purgées
  - Mode privé Safari : toast erreur explicite
- Pas de tests unitaires Angular (convention)

## 091-08 — Sync queue au retour en ligne + gestion 409

- **Epic parent** : Epic G Checkout tournée + offline
- **Estimation** : L
- **Dépendances** : **091-04** (409 force-unlock), **091-05** (snapshot), **091-07** (stockage queue)

### User story
**En tant que** Préleveur de retour en ligne après une session offline,
**Je veux** que mes actions en attente soient rejouées automatiquement vers le serveur dans l'ordre FIFO, avec une gestion propre des erreurs 409 (tournée déverrouillée par Admin) et 5xx (retry exponentiel),
**Afin que** mon travail terrain soit persisté côté serveur sans intervention manuelle.

### Contexte métier
Le retour en ligne est détecté via l'événement `online` de `navigator`. Le `SyncService` déclenche alors le replay de la queue. Chaque action pending contient le type (CREATE/UPDATE sampling, etc.) et le payload. On rejoue dans l'ordre FIFO (critique pour cohérence). Codes de retour :
- **2xx** → retirer action de la queue, succès silencieux (ou toast discret).
- **4xx hors 409** → retirer + log erreur utilisateur (ex. barcode dupliqué signalé trop tard, pas grand chose à faire).
- **409** spécifique `round.unlocked` → **purger toute la queue + clearSnapshot + toast persistant** "Tournée réinitialisée par admin".
- **5xx** → retry exponentiel (2s, 5s, 15s, puis abandon avec toast erreur).

### Critères d'acceptation

**Scénario 1 — Happy path : replay ordonné de la queue**
```gherkin
Étant donné le préleveur a saisi offline 3 prélèvements A, B, C (queue: [A, B, C])
Quand le réseau revient (événement 'online')
Alors SyncService.flushQueue() est déclenché
Et il envoie PUT /api/samplings/A → 200 OK → retire A de la queue
Puis PUT /api/samplings/B → 200 OK → retire B
Puis PUT /api/samplings/C → 200 OK → retire C
Et un toast discret "3 actions synchronisées" s'affiche
Et getPendingActions() retourne [] à la fin
```

**Scénario 2 — Edge case : 409 round.unlocked**
```gherkin
Étant donné la tournée a été force-unlock par un Admin pendant que le préleveur était offline
Et le préleveur a 5 actions pending
Quand le réseau revient et la première action est rejouée
Alors l'API retourne 409 Conflict { error: "round.unlocked" }
Et SyncService détecte le code d'erreur spécifique
Et purge immédiatement la queue entière (les 5 actions)
Et appelle offlineStorage.clearSnapshot(roundId)
Et affiche un toast rouge persistant "Votre tournée a été réinitialisée par un administrateur. Les saisies non synchronisées sont perdues."
Et redirige vers /sampling-rounds (liste)
```

**Scénario 3 — Permission / retry 5xx**
```gherkin
Étant donné une action en queue
Quand le serveur renvoie 503 Service Unavailable
Alors SyncService attend 2s puis retry
Puis si 503 à nouveau : attend 5s puis retry
Puis si 503 à nouveau : attend 15s puis retry
Puis si encore 5xx : abandonne + toast "Erreur serveur, réessayez plus tard"
Et l'action reste dans la queue (pas retirée, sera retentée au prochain événement online)
Et en cas de 400/422 (validation ex. champ invalide), l'action est retirée + toast erreur inline
Et en cas de 401 (session expirée), l'utilisateur est redirigé vers login sans purger la queue
```

### Tâches techniques

**Frontend — Service**
- `services/sync.service.ts` :
  - Signal `isSyncing`, `pendingCount`
  - Écoute `window.addEventListener('online', ...)` + check au démarrage si déjà online + actions en queue
  - Méthode `flushQueue()` : lecture FIFO, replay séquentiel via `ApiService`, gestion erreurs par code
  - Retry exponentiel sur 5xx : `[2000, 5000, 15000]` ms avec compteur `retries` persisté sur l'action
  - Sur 409 `round.unlocked` : `clearAll()` + toast + navigation
- Injection dans `app.component.ts` pour bootstrap

**Frontend — Intégration UI**
- Toasts unifiés via `MatSnackBar` avec libellés i18n
- Badge header (story 091-10) reflète `pendingCount`

**Backend — Support**
- Vérifier que toutes les endpoints concernées (PUT /api/samplings, POST /api/samplings, etc.) renvoient bien 409 avec `{ error: "round.unlocked" }` quand la tournée n'est plus locked par l'utilisateur (décorrélé du lock actif d'un autre user — ici le lock est simplement absent)
- Ajouter exception typée `RoundNotLockedByCurrentUserException` → 409

**Tests (obligatoires)**
- `SamplingServiceTest` :
  - `Update_WhenRoundNoLongerLockedByUser_ShouldThrowUnlockedConflict`
- Non-régression manuelle :
  - Scénario happy path online/offline/online
  - Scénario force-unlock pendant offline
  - Scénario 5xx simulé (kill backend, restart)
- i18n : clés `sync.{success,unlockedLost,retry,error401,error5xx}`

### Contexte métier
AquaPlan n'a actuellement aucun footer : impossible de savoir quelle version est déployée en un coup d'œil, ce qui complique le support. GitVersion calcule déjà la SemVer à chaque build côté .NET. Côté Angular, on doit exposer cette valeur à l'UI via un fichier `version.ts` généré au build (script pré-build npm qui interroge `dotnet gitversion`). Le footer est **non-sticky**, discret (gris clair, 11px), ne perturbe pas la mise en page. Nom développeur : "François Charrière" (hardcodé selon demande user).

### Critères d'acceptation

**Scénario 1 — Happy path : footer présent avec version**
```gherkin
Étant donné l'app AquaPlan est buildée avec GitVersion retournant SemVer "0.91.0"
Quand un utilisateur navigue sur n'importe quelle page
Alors un footer est présent en bas du contenu principal (non-sticky)
Et il affiche "AquaPlan v0.91.0 — Développé par François Charrière"
Et le style est discret : font-size 11px, color #9E9E9E, padding 8px 16px, text-align center
Et le footer reste sous le contenu (pas de position fixed qui recouvrirait les écrans)
```

**Scénario 2 — Edge case : fallback si version non générée**
```gherkin
Étant donné le script pré-build npm a échoué ou GitVersion n'est pas disponible
Quand l'app se charge
Alors le footer affiche "AquaPlan v0.91 — Développé par François Charrière" (version hardcodée fallback)
Et aucune erreur JS n'apparaît en console
Et la génération CI/CD doit journaliser un warning
```

**Scénario 3 — Permission / i18n**
```gherkin
Étant donné l'app en fr, de ou en
Quand le footer est rendu
Alors le texte "Développé par" est traduit ("Développé par" / "Entwickelt von" / "Developed by")
Et le nom "François Charrière" reste inchangé dans les 3 langues
Et le footer est visible pour tous les rôles (non conditionnel)
Et il reste affiché sur /login (avant authentification)
```

### Tâches techniques

**Frontend — Génération version**
- `AquaPlan.Web/ClientApp/scripts/generate-version.js` (Node) :
  ```js
  const { execSync } = require('child_process');
  const fs = require('fs');
  let version = 'v0.91'; // fallback
  try {
    version = 'v' + execSync('dotnet gitversion /showvariable SemVer').toString().trim();
  } catch (e) { console.warn('GitVersion unavailable, using fallback'); }
  fs.writeFileSync('src/environments/version.ts',
    `export const APP_VERSION = '${version}';\nexport const APP_AUTHOR = 'François Charrière';\n`);
  ```
- `package.json` : hook `"prebuild": "node scripts/generate-version.js"` et `"prestart": "node scripts/generate-version.js"`
- `.gitignore` : `src/environments/version.ts` (généré)

**Frontend — Composant**
- `components/footer/footer.component.ts` (standalone, OnPush) :
  ```ts
  @Component({ selector: 'app-footer', standalone: true,
    template: `<footer class="app-footer">
      AquaPlan {{ version }} — {{ 'footer.developedBy' | translate }} {{ author }}
    </footer>`,
    styles: [`.app-footer { text-align: center; font-size: 11px; color: #9E9E9E; padding: 8px 16px; }`] })
  export class FooterComponent {
    protected readonly version = APP_VERSION;
    protected readonly author = APP_AUTHOR;
  }
  ```
- `app.component.html` : insérer `<app-footer />` en fin du layout principal (après router-outlet, hors side nav)

**Frontend — i18n**
- Clés `footer.developedBy` (fr="Développé par", de="Entwickelt von", en="Developed by")

**Tests**
- Non-régression manuelle :
  - Footer visible sur login + pages authentifiées
  - Version matches `dotnet gitversion` output
  - Fallback hardcodé si script échoue
- Pas de tests unitaires Angular (convention)
