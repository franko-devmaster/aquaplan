## AQ-9-01 — Entité Container : domaine, migration et seed de 6 contenants

- **Epic parent** : AQ-9 Contenants
- **Estimation** : M
- **Dépendances** : aucune (première story du socle)

### User story
**En tant que** préleveur et administrateur,
**Je veux** disposer d'un référentiel de contenants (flacons) modélisé dans le domaine AquaPlan avec 6 contenants standards pré-seedés,
**Afin de** décrire le matériel physique à préparer pour chaque analyse et poser le socle des futures fonctionnalités (multi-barcodes, scan caméra, agrégation tournée).

### Contexte métier
Aujourd'hui, un profil d'analyse est abstrait : il n'indique pas dans quel flacon l'échantillon doit être prélevé. Le préleveur doit se baser sur sa mémoire et les conventions laboratoire, ce qui génère des erreurs de conditionnement et des ré-analyses coûteuses. L'introduction d'une entité `Container` posera les fondations du matériel physique géré dans l'application.

### Critères d'acceptation

**Scénario 1 — Happy path : migration et seed**
```gherkin
Étant donné une base AquaPlan à la version v0.7.1 sans table containers
Quand la migration "AddContainers" est appliquée et le seeder "AnalysisCatalogSeeder" exécuté
Alors la table "containers" existe avec les colonnes Id, Code, Name, Material, VolumeMl, Color, IsActive, TenantId
Et elle contient exactement 6 lignes avec les codes : BACT-V250, CHEM-PET500, CHEM-PEHD250, PHY-V100, PEST-V1000, ISOT-V60
Et chaque contenant a un unique volume (pas de doublon de type avec volume différent)
Et l'index unique (TenantId, Code) est créé
```

**Scénario 2 — Edge case : unicité par tenant**
```gherkin
Étant donné un tenant T1 avec le contenant "BACT-V250" déjà seedé
Quand on tente d'insérer un second contenant avec le code "BACT-V250" pour le tenant T1
Alors l'insertion échoue avec une violation de contrainte d'unicité
Mais le même code "BACT-V250" peut coexister pour un tenant T2 différent
```

**Scénario 3 — Permission / sécurité : isolation tenant**
```gherkin
Étant donné deux tenants T1 et T2 chacun avec leurs 6 contenants seedés
Quand un utilisateur authentifié du tenant T1 requête le DbSet Containers
Alors seuls les 6 contenants du tenant T1 sont retournés (filtrage global tenant actif)
Et aucun contenant du tenant T2 n'est visible
```

### Tâches techniques

**Backend — Domain**
- Créer `src/AquaPlan.Domain/Entities/Container.cs` (propriétés : Id, Code, Name, Material, VolumeMl, Color, IsActive, TenantId + audit fields)
- Ajouter enum `ContainerMaterial` si pertinent (Glass, BorosilicateGlass, AmberGlass, PET, HDPE)

**Backend — Infrastructure**
- Créer `Data/Configurations/ContainerConfiguration.cs` avec index unique `(TenantId, Code)`
- Ajouter `DbSet<Container>` dans `AquaPlanDbContext`
- Migration `AddContainers`
- Créer/étendre `Data/Seeds/AnalysisCatalogSeeder.cs` avec les 6 contenants (un seul volume par type)

**Tests**
- `tests/AquaPlan.Infrastructure.Tests/Seeds/AnalysisCatalogSeederTest.cs` — vérifier count = 6, codes attendus, isolation tenant
- Test migration : schéma après `AddContainers` correct

## AQ-9-02 — Service et API CRUD /api/containers (mutations Admin)

- **Epic parent** : AQ-9 Contenants
- **Estimation** : M
- **Dépendances** : **AQ-9-01** (entité + seed)

### User story
**En tant qu'** administrateur,
**Je veux** créer, consulter, modifier et désactiver des contenants via une API REST sécurisée,
**Afin de** gérer le catalogue matériel sans intervention base de données.

### Contexte métier
Les contenants évoluent (nouveaux flacons, fournisseurs, volumes) mais restent sous contrôle laboratoire. Seul un Admin peut muter le catalogue. Tous les rôles authentifiés peuvent le consulter pour la sélection dans les profils.

### Critères d'acceptation

**Scénario 1 — Happy path : CRUD complet Admin**
```gherkin
Étant donné un utilisateur authentifié avec le rôle Admin
Quand il appelle POST /api/containers avec un payload valide (Code, Name, Material, VolumeMl, Color)
Alors l'API retourne 201 Created avec le ContainerDto créé
Et GET /api/containers/{id} retourne ce contenant
Et PUT /api/containers/{id} permet de modifier Name/Material/VolumeMl/Color
Et PATCH /api/containers/{id}/toggle-status bascule IsActive
```

**Scénario 2 — Edge case : code en doublon**
```gherkin
Étant donné un contenant existant "BACT-V250" dans le tenant courant
Quand un Admin envoie POST /api/containers avec Code = "BACT-V250"
Alors l'API retourne 409 Conflict (ou 400 avec message explicite)
Et aucun contenant supplémentaire n'est créé
```

**Scénario 3 — Permission : rôle non-Admin en mutation**
```gherkin
Étant donné un utilisateur authentifié avec un rôle non-Admin (Préleveur, Viewer)
Quand il appelle POST, PUT ou PATCH sur /api/containers
Alors l'API retourne 403 Forbidden
Mais GET /api/containers retourne bien 200 OK avec la liste
```

### Tâches techniques

**Backend — Application**
- `Application/DTOs/Containers/` : `ContainerDto`, `ContainerListDto`, `ContainerAddDto`, `ContainerUpdateDto`, `ContainerFilteringInputDto`
- `Application/Services/Interfaces/IContainerService.cs`

**Backend — Infrastructure**
- `Infrastructure/Services/ContainerService.cs` (CRUD + toggle, filtrage tenant, validations)

**Backend — API**
- `Api/Controllers/Api/ContainersController.cs` avec `[ApiController]`, `[Route("api/[controller]")]`, `[Authorize]`
  - `GET /api/containers` (tous rôles)
  - `GET /api/containers/{id}` (tous rôles)
  - `POST /api/containers` (`[Authorize(Roles = "Admin")]`, `[Audited]`)
  - `PUT /api/containers/{id}` (`[Authorize(Roles = "Admin")]`, `[Audited]`)
  - `PATCH /api/containers/{id}/toggle-status` (`[Authorize(Roles = "Admin")]`, `[Audited]`)
- DI : `Api/Program.cs` — `builder.Services.AddScoped<IContainerService, ContainerService>()`

**Tests (obligatoires)**
- `tests/AquaPlan.Application.Tests/Services/ContainerServiceTest.cs` — happy path CRUD, filtrage tenant, code doublon
- `tests/AquaPlan.Api.Tests/Controllers/ContainersControllerTest.cs` — attributs HTTP, routes, rôles, 201/403/409

## AQ-10-01 — AnalysisProfile.ContainerId obligatoire + picklist + backfill par Category

- **Epic parent** : AQ-10 Profils → Contenants, Mandats → Programmes
- **Estimation** : M
- **Dépendances** : **AQ-9-01** (entité Container + seed)

### User story
**En tant que** responsable catalogue,
**Je veux** que chaque profil d'analyse soit obligatoirement rattaché à un contenant, avec backfill automatique des profils existants selon leur `Category`,
**Afin que** le préleveur voie immédiatement le flacon à préparer lorsqu'un mandat intègre un profil.

### Contexte métier
Sans lien profil → contenant, la nouvelle entité `Container` reste décorative. Ce lien devient la clé qui permettra, plus tard (v0.9), d'agréger automatiquement le matériel d'une tournée. Le backfill par `Category` sécurise la migration des données existantes sans intervention manuelle.

### Critères d'acceptation

**Scénario 1 — Happy path : backfill par catégorie**
```gherkin
Étant donné une base avec des profils existants aux catégories Bacteriology, Chemistry, Physical, Other
Quand la migration "AddContainerIdToAnalysisProfile" est appliquée
Alors chaque profil Bacteriology a ContainerId = Id(BACT-V250)
Et chaque profil Chemistry a ContainerId = Id(CHEM-PET500)
Et chaque profil Physical a ContainerId = Id(PHY-V100)
Et chaque profil Other a ContainerId = Id(CHEM-PET500)
Et la colonne container_id est marquée NOT NULL après le backfill
Et la contrainte FK est en OnDelete Restrict
```

**Scénario 2 — Edge case : création profil sans contenant rejetée**
```gherkin
Étant donné un Admin sur le formulaire de création d'un profil d'analyse
Quand il soumet le formulaire sans sélectionner de contenant
Alors la validation frontend bloque l'envoi avec un message "Contenant requis"
Et si la requête API POST /api/analysis-profiles est envoyée sans ContainerId
Alors l'API retourne 400 Bad Request
```

**Scénario 3 — Permission / intégrité : suppression contenant utilisé**
```gherkin
Étant donné un contenant "BACT-V250" utilisé par au moins un profil
Quand un Admin tente de supprimer physiquement ce contenant
Alors la base rejette la suppression (FK Restrict) et l'API retourne 409 Conflict
Mais l'Admin peut désactiver le contenant (IsActive = false) via toggle-status
Et un contenant inactif n'apparaît plus dans la picklist de création de profil
```

### Tâches techniques

**Backend — Domain**
- `AnalysisProfile` : ajouter `ContainerId` + navigation `Container`

**Backend — Infrastructure**
- `AnalysisProfileConfiguration` : FK `ContainerId` obligatoire, `OnDelete(Restrict)`
- Migration `AddContainerIdToAnalysisProfile` :
  1. Ajouter `container_id` nullable
  2. Backfill par `Category` (UPDATE SQL vers les 6 codes seedés)
  3. Passer la colonne à `NOT NULL`
- `AnalysisProfileService` : `.Include(Container)`, validation ContainerId actif à la création/update

**Backend — Application**
- DTOs `AnalysisProfileDto`, `AnalysisProfileAddDto`, `AnalysisProfileUpdateDto` : ajouter `ContainerId`, `ContainerCode`, `ContainerName`

**Frontend**
- `models/analysis-profile.model.ts` : ajouter containerId/Code/Name
- `pages/analysis-catalog/analysis-profiles.component.ts` : picklist `mat-select` alimentée par `ContainerDatastore` (filtrée `IsActive`), champ requis

**Tests**
- `AnalysisProfileServiceTest` : création sans ContainerId → échec, Include Container OK
- Test migration : backfill mapping correct par Category

## AQ-10-02 — Relation Order ↔ AnalysisProgram (remplace ↔ AnalysisProfile) + pré-script audit orphelins

- **Epic parent** : AQ-10 Profils → Contenants, Mandats → Programmes
- **Estimation** : XL
- **Dépendances** : **AQ-10-01** (profils rattachés à un contenant)

### User story
**En tant que** responsable catalogue et officier cantonal,
**Je veux** qu'un mandat soit rattaché à des **programmes d'analyse** (et non plus à des profils bruts), avec un pré-script qui traite automatiquement les profils orphelins avant bascule,
**Afin de** travailler à la bonne granularité métier (programme = usage réglementaire) sans perte de données.

### Contexte métier
Un mandat devrait logiquement porter un "Programme d'analyse eau potable saisonnier" plutôt qu'une liste de profils hétérogènes. Les préleveurs raisonnent en programmes, pas en profils. Cette bascule introduit un risque : les profils non rattachés à un programme (orphelins) deviendraient invisibles des mandats. D'où le pré-script qui crée automatiquement un programme `PROG-{profileCode}` pour chaque profil isolé, garantissant zéro perte.

### Critères d'acceptation

**Scénario 1 — Happy path : migration complète avec bascule**
```gherkin
Étant donné une base avec des mandats référençant des profils via order_analysis_profiles
Et tous les profils sont déjà rattachés à au moins un programme
Quand la migration "ReplaceOrderProfilesByPrograms" est appliquée
Alors la table "order_analysis_programs" existe
Et elle contient une ligne DISTINCT par (OrderId, ProgramId) déduite via analysis_program_profiles
Et la table "order_analysis_profiles" est supprimée
Et aucun mandat ne perd de programme implicite (count preservé ou supérieur)
```

**Scénario 2 — Edge case : profils orphelins automatiquement encapsulés**
```gherkin
Étant donné une base avec des profils non rattachés à aucun programme (orphelins)
Quand la migration "BackfillOrphanedProfilesAsPrograms" s'exécute (avant ReplaceOrderProfilesByPrograms)
Alors pour chaque profil orphelin de code "XYZ", un programme "PROG-XYZ" est créé
Et une ligne analysis_program_profiles est créée pour rattacher le profil à ce programme
Et un enregistrement est ajouté dans audit_log avec le type "OrphanProfileWrapped"
Et après exécution, la requête SELECT COUNT(*) FROM analysis_profiles WHERE id NOT IN (SELECT analysis_profile_id FROM analysis_program_profiles) retourne 0
```

**Scénario 3 — Permission / UI : dialogs basculent sur programmes**
```gherkin
Étant donné un utilisateur autorisé à créer ou éditer un mandat
Quand il ouvre order-create-dialog, order-edit-dialog ou round-add-order-dialog
Alors la picklist affiche des "Programmes d'analyse" et non plus des "Profils"
Et le payload envoyé au backend contient analysisProgramIds (et non plus analysisProfileIds)
Et GET /api/orders/{id} retourne analysisPrograms[] avec les infos de chaque programme
Et un appel forgé avec analysisProfileIds retourne 400 Bad Request (champ ignoré/refusé)
```

### Tâches techniques

**Backend — Domain**
- Créer `Domain/Entities/OrderAnalysisProgram.cs` (remplace `OrderAnalysisProfile` supprimé)
- `Order.cs` : navigation `ICollection<OrderAnalysisProgram> OrderAnalysisPrograms`
- Supprimer navigation `OrderAnalysisProfiles` de `Order`

**Backend — Infrastructure**
- `Data/Configurations/OrderAnalysisProgramConfiguration.cs`
- `AquaPlanDbContext` : DbSet + suppression ancien DbSet
- Migration `BackfillOrphanedProfilesAsPrograms` (pré-script) :
  - Détecte profils non présents dans `analysis_program_profiles`
  - Crée programme `PROG-{profileCode}` par profil orphelin
  - Insère ligne `analysis_program_profiles`
  - Insère ligne `audit_log`
- Migration `ReplaceOrderProfilesByPrograms` :
  - Créer `order_analysis_programs`
  - `INSERT ... SELECT DISTINCT OrderId, ProgramId FROM order_analysis_profiles JOIN analysis_program_profiles ...`
  - DROP `order_analysis_profiles`
- `OrderService` : remplacer `.Include(OrderAnalysisProfiles)` par `.Include(OrderAnalysisPrograms).ThenInclude(AnalysisProgram)` (lignes 146, 204, 226, 263, 465)
- `SamplingRoundService` : renommer `AnalysisProfileNames` → `AnalysisProgramNames`

**Backend — Application**
- DTOs : `OrderCreateDto`, `OrderUpdateDto`, `OrderDetailDto` → `analysisProgramIds`, `analysisPrograms[]` avec `OrderAnalysisProgramDto`
- `SamplingRoundDtos` : `AnalysisProgramNames`

**Frontend**
- `models/order.model.ts` : `analysisProgramIds`, `OrderAnalysisProgramDto`
- `models/sampling-round.model.ts` : `analysisProgramNames`
- `datastore/order.datastore.ts` : `analysisProgramIds`
- `pages/orders/order-create-dialog.component.ts`, `order-edit-dialog.component.ts` (ligne 143), `order-detail.component.ts` : bascule programmes
- `pages/sampling-rounds/round-add-order-dialog.component.ts`, `sampling-round-detail.component.ts` : bascule programmes
- i18n : nouvelles clés `orders.programs.*`

**Tests**
- `OrderServiceTest` : création mandat avec programmes, Include chaîné
- Test migration orphelins : scénario setUp 3 profils dont 1 orphelin → post-migration 0 orphelin + 1 programme `PROG-*` + 1 audit_log
- Test migration bascule : count préservé sur jeu de données synthétique

### Note critique
Migrations à appliquer dans l'ordre strict : **AddContainerIdToAnalysisProfile → BackfillOrphanedProfilesAsPrograms → ReplaceOrderProfilesByPrograms**. Toute rupture d'ordre peut provoquer perte de données. Exécuter `dotnet ef database update --dry-run` en pré-prod d'abord.

## AQ-10-03 — Détail programme : affichage des contenants uniques dédupliqués

- **Epic parent** : AQ-10 Profils → Contenants, Mandats → Programmes
- **Estimation** : S
- **Dépendances** : **AQ-10-01** (profils rattachés à un contenant)

### User story
**En tant que** préleveur ou responsable catalogue,
**Je veux** voir sur la page de détail d'un programme la liste **unique** des contenants requis (un même contenant partagé par plusieurs profils n'apparaît qu'une seule fois),
**Afin de** préparer le matériel sans compter en double.

### Contexte métier
Un programme regroupe souvent plusieurs profils qui partagent le même contenant (ex. 3 profils bactério utilisent tous un BACT-V250). L'affichage brut produit des doublons visuellement déroutants. La déduplication est cognitivement critique pour la préparation terrain.

### Critères d'acceptation

**Scénario 1 — Happy path : déduplication**
```gherkin
Étant donné un programme contenant 3 profils : P1 (BACT-V250), P2 (BACT-V250), P3 (CHEM-PET500)
Quand on ouvre GET /api/analysis-programs/{id}
Alors le DTO retourne requiredContainers = [{BACT-V250}, {CHEM-PET500}]
Et la page de détail affiche 2 contenants (et non 3)
```

**Scénario 2 — Edge case : programme sans profils**
```gherkin
Étant donné un programme ne contenant aucun profil d'analyse
Quand on consulte son détail
Alors requiredContainers est un tableau vide []
Et la page affiche un message "Aucun contenant requis" (pas d'erreur, pas de spinner infini)
```

**Scénario 3 — Permission : accès lecture tous rôles authentifiés**
```gherkin
Étant donné un utilisateur authentifié (rôle quelconque : Admin, Préleveur, Viewer)
Quand il accède à /analysis-programs/{id}
Alors il voit la liste dédupliquée des contenants
Et la modification du programme reste soumise à [Authorize(Roles = "Admin")]
```

### Tâches techniques

**Backend**
- `AnalysisProgramService` : calculer `RequiredContainers` = `Profils.Select(p => p.Container).DistinctBy(c => c.Id).ToList()`
- `AnalysisProgramDto` : ajouter `RequiredContainers[]` avec `ProgramContainerDto` (Id, Code, Name, Material, VolumeMl, Color)

**Frontend**
- `models/analysis-program.model.ts` : `requiredContainers[]`
- `pages/analysis-catalog/analysis-programs.component.ts` : section "Contenants requis" listant les contenants dédupliqués (puces ou tableau)

**Tests**
- `AnalysisProgramServiceTest` : `GetById_WithDuplicateContainers_ShouldReturnDistinct`
- Test programme vide → requiredContainers = []

## AQ-12-01 — Tuile dashboard renommée "Mandats à finaliser"

- **Epic parent** : AQ-12 Tableau de bord cliquable
- **Estimation** : S
- **Dépendances** : aucune (peut démarrer en parallèle)

### User story
**En tant qu'** utilisateur du dashboard,
**Je veux** que la tuile des mandats en cours soit renommée **"Mandats à finaliser"** et qu'elle agrège les statuts `InProgress` et `Completed`,
**Afin que** le libellé reflète l'action attendue (finaliser = transmettre ou clôturer) et que le compteur couvre l'ensemble du travail en attente.

### Contexte métier
Le libellé actuel ambigu ("Mandats en cours") ne distingue pas les mandats qui nécessitent encore une action (finalisation, transmission LIMS) de ceux qui sont terminés. L'agrégation `InProgress + Completed` donne au chef d'équipe une vue exhaustive du backlog opérationnel.

### Critères d'acceptation

**Scénario 1 — Happy path : compteur agrégé**
```gherkin
Étant donné une base avec 5 mandats InProgress et 3 mandats Completed
Quand j'ouvre la page d'accueil
Alors la tuile "Mandats à finaliser" affiche le compteur 8
Et le libellé est "Mandats à finaliser" dans les 3 langues (fr/de/en)
```

**Scénario 2 — Edge case : aucun mandat à finaliser**
```gherkin
Étant donné une base sans mandat InProgress ni Completed
Quand j'ouvre la page d'accueil
Alors la tuile affiche 0 sans erreur
Et elle reste cliquable (navigue vers liste filtrée vide)
```

**Scénario 3 — Permission : visibilité par rôle**
```gherkin

Étant donné un utilisateur sur la page d'accueil
```

```gherkin
Alors la tuile "LDP à valider" est masquée (ou affichée mais non cliquable selon design final)
```

## AQ-13-02 — Dialog round-add-order : suppression du mode "link existing", toujours création

- **Epic parent** : AQ-13 UX polish
- **Estimation** : S
- **Dépendances** : peut précéder AQ-10-02 (le dialog sera de toute façon retouché pour la bascule programmes)

### User story
**En tant que** préleveur ou chef d'équipe,
**Je veux** que le dialog "Ajouter un mandat" depuis une tournée ouvre directement le formulaire de création (sans radio "Créer nouveau / Lier existant"),
**Afin de** simplifier le workflow terrain, supprimer une décision inutile et prévenir les rattachements erronés.

### Contexte métier
Le mode "link existing" introduit un risque de double-rattachement (un mandat lié à deux tournées) et n'a aucun sens métier validé : un mandat appartient à une et une seule tournée de référence. Le retirer supprime 80% des erreurs utilisateur identifiées en session de test v0.7.

### Critères d'acceptation

**Scénario 1 — Happy path : ouverture dialog**
```gherkin
Étant donné une tournée affichée en édition
Quand l'utilisateur clique "Ajouter un mandat"
Alors le dialog s'ouvre directement sur le formulaire de création d'un nouveau mandat
Et aucun radio button "Créer nouveau / Lier existant" n'est présent
Et la soumission crée un mandat et le rattache à la tournée
```

**Scénario 2 — Edge case : tentative de re-rattachement via API**
```gherkin
Étant donné un mandat M1 déjà rattaché à la tournée T1
Quand un appel forgé tente de rattacher M1 à la tournée T2
Alors l'API retourne 409 Conflict ou 400 Bad Request avec message explicite
Et M1 reste rattaché à T1 uniquement
```

**Scénario 3 — Permission : rôle autorisé**
```gherkin
Étant donné un utilisateur sans le rôle Préleveur ni Admin
Quand il tente d'ouvrir le dialog d'ajout de mandat à une tournée
Alors le bouton "Ajouter un mandat" n'est pas affiché
Et l'appel API de création de mandat rattaché retourne 403 Forbidden
```

### Tâches techniques

**Frontend**
- `pages/sampling-rounds/round-add-order-dialog.component.ts` :
  - Supprimer radio group `mode: 'create' | 'link'`
  - Supprimer sélection "mandat existant"
  - Ne laisser que le formulaire de création
  - Nettoyer imports et tests de template

**Backend**
- `OrderService` ou `SamplingRoundService` : verrou fonctionnel pour empêcher un mandat d'être rattaché à deux tournées (si pas déjà en place)

**Tests**
- `RoundAddOrderDialog` — Gherkin L3 UI : absence radio, création directe fonctionnelle
- Test backend rattachement double → refus
